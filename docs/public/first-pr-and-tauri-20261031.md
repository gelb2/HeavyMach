# 첫 PR을 받다. 그 다음 이어진 스케일업, 그리고 타우리

공개 저장소에서 처음으로 다른 사람이 보낸 PR을 받았다. HeavyMach를 웹브라우저에서 실행하게 만든 작업이었다. 나는 이 게임을 복원하면서 웹으로 돌린다는 발상을 한 적이 전혀 없었다.

시간이 얼마 남지 않은 자가 만든 게임 복원 프로젝트에, 다른 사람이 자신의 귀중한 시간을 투자했다. [fastutlego가 보낸 PR #24](https://github.com/gelb2/HeavyMach/pull/24)였다. 내가 보기에는 기술적으로도 완성도가 높았다. 어떻게 받아들이고, 무엇을 보존하며, 이 사람이 만든 것을 어디까지 이어 갈 것인가를 고민했다.

## 기존 앱과 웹판

나에겐 소소하고 애매한 고민거리가 있었다. Android는 이미 네이티브 앱으로 돌아가고 있었다. 이 웹판을 받아들이면 Android 네이티브로 만든 것을 엎어야 하는가? 그렇다면 iOS 네이티브는 왜 존재해야 하는가?

그와 동시에 다른 질문도 있었다. 이 사람의 기여를 온전히 프로젝트에 남기고 공식 기록으로 만들면서, 이 사람이 이룬 기술적 성취를 복원된 게임에 어떻게 구현할 것인가?

나는 혼자 고민하던 다른 문제를 떠올렸다. Windows·Mac·웹은 어떻게 할 것인가. 그 문제를 떠올린 다음 PR을 다시 확인했다.

기존 iOS·Android·Mac 앱은 유지하고 웹판을 추가하기로 했다. 이 웹판으로 Windows와 Mac용 앱을 만드는 방법도 검토하기로 했다.

## PR 승인하는 방법까지 기계한테 가르쳐야 할까

내가 기대한 순서는 검토하고, 필요한 문제를 고치고, 그 결과를 PR 리뷰에 남겨 승인한 뒤 병합하는 것이었다. 이 사람이 투자한 시간을 존중하고 기여를 정식으로 남기려는 작업이었다. 커밋이 훼손되거나 Contributors에서 빠지는 일도 없어야 한다고 여러 번 말했다.

Codex는 코드를 검토하고 수정과 테스트를 했다. 그런데 GitHub의 `Approve` 리뷰는 남기지 않은 채 바로 머지했다. 내가 물으니 별도의 승인 리뷰는 남기지 않았다고 답했다.

PR 승인하는 방법까지 기계한테 가르쳐야 할까? 내게는 iOS에서 리스트 형태의 UI를 만들려면 테이블뷰나 컬렉션뷰를 쓰면 된다는 수준의 사안이다. Codex가 `Approve`를 누르지 않고 다이렉트로 머지하는 것을 보고 나는 화가 치밀었다.

나는 기여자의 웹판으로 Windows·Mac 앱을 만들 방법을 검토하라고 지시했다. 그런데 PR에 검토 결과와 승인을 남기는 순서까지 다시 지정해야 했다.

## 기여받은 웹판의 구현

PR은 기존 C++ 게임 코어를 Emscripten으로 빌드해 WebAssembly에서 실행했다. 브라우저에 맞는 입력·음향·저장과 WebGL2 렌더러, HUD 편집, 자동 검사도 들어 있었다. 웹 실행부는 `Sources/Web/`, 빌드와 브라우저 구성은 `Web/`에 분리돼 있었다. [웹 이식 문서](../web-port-20261028.md).

전투·미션 처리는 기존 C++ 코어를 재사용했다. 웹 전용 코드는 별도 폴더에 있어 기존 iOS·Android 앱을 유지하면서 웹판을 추가할 수 있었다.

나는 Codex에게 바로 머지하지 말고 먼저 비교하라고 했다. develop과의 차이, 리베이스 전후의 구현 보존, 기존 iOS·Android에 미칠 영향, 저장과 로드, 기여자 기록까지 확인하도록 했다.

검토에서는 업그레이드 창이 열린 뒤에도 전투가 진행되는 문제, 브라우저 저장을 읽지 못했을 때 기존 진행을 덮어쓸 수 있는 문제, WebGL 컨텍스트를 잃은 뒤 화면이 복구되지 않는 문제가 재현됐다. Codex는 웹 전용 코드에서 이를 수정했다. 원저자의 작업은 원래 19개 커밋으로 두고, 수정과 검사 기록은 두 개의 후속 커밋으로 추가했다. [문제와 수정 결과](../reviews/pr24-web-review-20261031.md#fixes-and-merge).

## Tauri와 Electron 비교

나는 Electron을 손으로 잠깐 다뤄 본 적이 있다. 소스 구조와 웹뷰를 불러오는 과정이 불안정하게 느껴졌고, 자원도 많이 쓰는 것 같았다. 그 경험 때문에 Tauri가 더 적합한지 물었다. HeavyMach가 Vue로 만든 프로젝트가 아닌데도 사용할 수 있는지도 확인하고 싶었다.

Tauri는 기존 HTML·JavaScript·Wasm을 앱에 넣고, 창과 파일 저장 같은 기능을 Rust 쪽에 붙일 수 있다. Mac에서는 WKWebView, Windows에서는 WebView2를 사용한다. Electron은 Chromium과 Node를 포함하며 main·renderer·preload 사이에 역할을 나눈다. [Tauri 프런트엔드](https://v2.tauri.app/start/frontend/), [Tauri 웹뷰](https://v2.tauri.app/reference/webview-versions/), [Electron 구조](https://www.electronjs.org/docs/latest/tutorial/process-model).

| 실행 환경 | 사용할 구현 |
| --- | --- |
| iPhone·iPad | 현재 네이티브 앱 유지 |
| Android | 현재 네이티브 앱 유지 |
| Mac | 현재 AppKit 앱 유지. Tauri 기반 앱은 별도 후보로 비교 |
| Windows | 같은 Tauri 프로젝트로 설치본 빌드. 실행 검사는 후속 과제 |
| 웹브라우저 | 같은 웹판을 정적 호스팅에서 실행 |

Tauri는 OS의 웹뷰를 사용하므로 브라우저 엔진을 앱에 포함하지 않아도 된다. Mac과 Windows는 서로 다른 엔진을 쓰므로 각각 검사해야 한다. Electron은 두 OS에 같은 Chromium 버전을 배포할 수 있다. 게임 실행 중에는 두 방식 모두 텍스처·음향·Wasm 메모리를 사용한다.

Tauri Mac 앱부터 만들고 기존 네이티브 Mac 앱과 같은 미션·무기·화면 조건으로 비교하기로 했다. 시작 시간, 전체 프로세스 메모리, 전투 중 화면 갱신 간격과 저장·음향·복귀를 확인한다. 그다음 브라우저와 PWA로 실행할 웹판을 배포하고 Windows 설치본을 빌드한다. Electron은 기술 비교 자료로 남긴다.

## 게임 진행 저장

처음에는 웹뷰로 게임을 띄우면 진행이 저장되지 않는 것이 아닌가 생각했다. 확인해 보니 이 PR에는 이미 IndexedDB 저장이 있었다. Emscripten의 IDBFS를 통해 `HvM.dat`를 브라우저 저장소에 남긴다. 이번 검토에서 초기 읽기 실패와 쓰기 실패를 다루는 부분을 보완했다. [Emscripten 파일 시스템](https://emscripten.org/docs/api_reference/Filesystem-API.html).

순수 웹판은 이 저장 경로를 유지할 수 있다. 배포 주소와 자원 버전을 관리하고, 브라우저 데이터 삭제나 저장 공간 정리, 업데이트 상황을 검사해야 한다. 홈 화면에 설치하고 인터넷 없이 플레이할 수 있도록 PWA도 이 단계에 포함하라고 했다. 게임 파일을 모두 받은 뒤 비행기 모드에서 플레이하고, 저장한 다음 앱을 껐다 켜도 이어지는지 검사한다. 내보내기·가져오기는 별도 시작 화면에 추가할 계획이다.

내가 Tauri를 고려한 이유는 저장 데이터를 보존하고 Mac·Windows까지 지원하기 위해서다. 기여자의 웹 구현과 Codex의 후속 수정 3건은 더 고치지 않고 사용하라고 했다. 새 앱을 만든다는 이유로 정상 동작하는 웹판까지 다시 수정하는 일을 막으려는 조건이다.

현재 계획은 웹판의 IndexedDB·localStorage를 유지하고, 별도 실행기가 이미 저장된 진행과 설정을 OS 앱 데이터 폴더에 백업하는 것이다. 웹뷰 저장소가 사라지면 게임을 열기 전에 파일에서 복구한다. 정상 종료 때는 마지막 백업을 기다리고, 외부 파일로 내보내고 가져오는 기능도 새 실행기에 둔다. 앱 데이터 전체를 지웠을 때는 별도 내보낸 파일이 필요하다. 백업 연결과 복구 검사는 앞으로 구현한다. [데이터 보존 계획](../desktop-web-plan-20261031.md).

저장 시점은 현재 게임의 규칙을 유지한다. 발사 때마다 파일을 쓰던 문제를 앞서 고쳤으므로, 데스크톱판에서도 발사 처리와 저장 처리를 분리한다.
