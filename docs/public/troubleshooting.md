# HeavyMach 트러블슈팅

<!-- language-nav:start -->
[한국어](troubleshooting.md) | [English](../en/public/troubleshooting.md)
<!-- language-nav:end -->

나는 직접 플레이하면서 원작과 다른 움직임·사격·그림·성능을 지적했다. Codex는 자신이 작성한 코드에서 차이를 찾고, 해당 경로를 수정한 뒤 같은 조건으로 검사했다.

## 1. 사격·피격 때마다 파일 저장

나는 “발사 때마다 파일을 저장?”이라고 물었다. 초기 코드는 탄약·피격·경험치의 메모리 변경 통지 `changed()`를 파일 저장에 연결했다. 전투가 계속되는 동안 작은 상태 변화가 매번 디스크 쓰기로 이어졌다.

문제는 게임 상태 갱신과 영구 저장의 결합이었다. Codex는 메모리 값은 즉시 갱신하되 파일 쓰기는 슬롯 선택·다음 스테이지·게임 오버·메뉴 복귀 네 시점으로 분리했다. 저장 형식 3,624바이트는 유지했다.

수정 뒤 자동 검사에서 180프레임 사격 중 파일 쓰기 0회, 메뉴 복귀 1회, 백그라운드 전환 0회가 기록됐다. 이후 키보드 입력과 항공기 추가에도 같은 원칙을 적용했다. [실행 정책](../runtime-policy.md), [저장 검사](../../Tests/iOS/HMSaveParityTests.mm)

## 2. UIKit에서 게임 그림을 매 프레임 생성

나는 정상 동작한 기준에서는 프레임 드랍이 없었는데 새 앱에서 발생한다고 지적했다. “UIKit으로 게임 그래픽 렌더링 하는 것 자체”의 타당성을 물었고, 기존 그래픽 경로와 비교하도록 지시했다.

초기 렌더링에는 CPU 픽셀 연산·행 뒤집기·메모리 복사·이미지 객체 생성과 합성이 있었다. 스프라이트를 GPU에서 그릴 수 있는 장면을 CPU에서 반복 처리했다. 오프스크린 120표본에서 슬롯 메뉴 20.187ms, 사격 19.506ms로 16.67ms를 넘었다.

Codex는 OpenGL ES 1.1 경로를 복원하고 텍스처를 재사용했다. 업로드 뒤 필요 없는 CPU 픽셀 메모리를 해제했다. 이 변경 뒤에도 표시·음향·타이머 비용을 따로 검사했다. 수정 뒤 내가 iPhone에서 직접 플레이했을 때 프레임 드랍은 보이지 않았다. [렌더링 정책](../rendering-policy.md), [이행 기록](../opengl-migration-20261024.md)

## 3. 사격 효과음 재시작 지연

렌더링 변경만으로 사격 지연을 설명할 수 없었다. Codex가 효과음을 `AVAudioPlayer`로 재시작하는 호출을 측정하니 평균 52.887ms, p95 58.549ms가 나왔다.

Codex는 OpenAL 버퍼·소스를 미리 만들고 발사 때 재사용하도록 바꿨다. OpenAL 재생 호출 비용은 평균 0.007053ms, p95 0.008167ms였다. [음향 계약·실행 정책](../runtime-policy.md), [OpenAL 검사](../../Tests/iOS/HMOpenALAudioTests.mm)

## 4. 시간 누적 계산으로 달라진 진행

나는 시간 누적 로직을 왜 넣었는지 물었다. 초기 구현은 실제 경과 시간을 누적하고 필요한 횟수만큼 게임 tick을 실행했다. 한 표시 호출에서 게임이 0회 또는 2회 진행되면서 원래의 이동·사격 감각과 달라질 수 있었다.

Codex는 표시 호출마다 게임을 한 번 갱신하도록 맞추고 타이머 마감 시각을 조정했다. 일시정지·복귀 때 누적된 시간을 따라잡는 처리를 없앴다. 이동·무기·시간 검사는 이 규칙을 기준으로 실행한다. [실행 정책](../runtime-policy.md)

## 5. 약 32ms 지연을 하나의 원인으로 설명

나는 캔버스·좌표·화면 제출 등 기준과 다르게 구현한 부분을 비교하라고 요구했다. 타이머 간격, 게임 처리 시간, 화면 제출 대기를 섞어 설명하면 실제로 고칠 위치가 드러나지 않았다.

Codex는 Instruments와 프레임 계측을 연결해 호출 간격·CPU 처리·표시 경로를 분리했다. Mac에서는 `flushBuffer`와 표면 갱신, iPad Simulator에서는 소프트웨어 픽셀 채우기가 큰 비용을 차지했다. Mac 수정 결과와 Simulator·실기기의 남은 기준 실패는 [검증 표](validation.md)에 각각 기록했다.

## 6. 틸트 반전과 가로 화면 회전

일반 앱 설치 후 나는 틸트 방향이 뒤집혔다고 지적했다. Codex가 센서 축, 기기의 가로 방향, 게임 이동 축을 연결하는 부분을 고쳤다. 이후 나는 왼쪽·오른쪽 가로 회전에 맞춰 화면과 입력을 변환하도록 요구했다.

Codex는 터치와 센서 변환을 좌표 정책에 묶고 두 가로 방향에서 사격·이동을 검사했다. 내가 직접 확인했을 때 화면 회전은 정상적으로 동작했다. 키보드는 같은 이동 경로에 가상 기울기를 전달하며 Shift로 작은 값을 만들 수 있다. [좌표 정책](../coordinate-policy.md), [입력 정책](../keyboard-input-policy.md)

## 7. 공중 지원 공격이 탱크 뒤로 낙하

나는 포탄·미사일·레이저 지원 공격 상당수가 터치한 곳보다 탱크 뒤로 떨어진다고 지적했다. 터치 해제 때 전달한 가짜 좌표가 낙하 지점 계산에 들어갔다.

Codex는 해제 입력과 유효한 조준 좌표를 분리하고 마지막 공격 좌표를 유지했다. 나는 치트 앱에서 모든 무기를 검사하는 절차도 요구했다. Codex가 이후 무기별 선택·발사·충돌·해제 입력을 공통 검사에 넣었다. [수정 기록](../weapon-result-fix-20261025.md), [전체 무기 검사](../weapon-validation-procedure.md)

## 8. 미션 결과 일러스트 누락과 월드 노출

미션 클리어 뒤 그림이 나오지 않는다고 지적하자 Codex가 자원 이름을 대조했다. JPG·PNG 접미사 대응이 잘못돼 결과 그림을 찾지 못하는 경로가 있었다. 이를 수정한 뒤 내가 실제 폰에서 그림을 확인했다.

넓은 화면에서는 결과 그림 밖으로 전장이 보였다. Codex는 결과 화면이 전체 캔버스를 덮도록 배경과 표시 영역을 고쳤다. 그림 로드와 화면 덮기를 별개로 검사했다. [그림 수정](../clear-illustration-fix-20261025.md), [결과 화면 수정](../weapon-result-fix-20261025.md)

## 9. 넓어진 화면에서 보스가 너무 일찍 접근

나는 미션3-5 항공기형 보스가 왼쪽으로 빨리 접근하고 오른쪽으로 잘 돌아가지 않는다고 했다. Codex는 처음에 대상을 헬기로 잘못 식별했다. 내가 항공기라고 정정한 뒤 Codex가 Stage14의 Boss05·E_Boss02를 대조했다.

화면 폭을 넓히자 기존의 가시성 판정과 전투 활성 조건이 더 일찍 충족될 수 있었다. 단순한 이동 속도 조절로 처리할 문제가 아니었다. Codex는 표시 범위와 보스 전투 활성 시점을 분리하고 해당 미션을 검사했다. 이후 내가 전체 미션을 직접 플레이했을 때 적 움직임 이상은 보이지 않았다. [보스 조사·수정](../boss-motion-fix-20261025.md)

## 10. 배경 연결·검은줄·도어 범위

메뉴 좌우에 추가한 그림이 중앙과 이어지지 않아 내가 수정을 요구했다. Codex는 연결부의 구조·명암·색을 맞춘 뒤 치트 앱에서 확인했다. 타이틀 경계의 검은줄은 텍스처 여백이 UV에 섞이는 경로를 수정했다.

나는 기존 영역과 새 영역이 따로 열리고 닫히던 전환을 전체 화면 도어로 바꾸도록 했다. Codex가 네 도어 조각의 배치와 크기를 수정했다. 중앙 표식 크기를 유지하고 바깥 면을 늘리는 네 조각을 사용한다. HUD 클립을 해제하고 실제 캔버스에 맞춰 그린다. 닫힐 때 소수점 경계에서 틈이 생기지 않도록 표시 좌표를 정수화했다. 99tick 전환과 효과음 순서, 여러 화면 비율을 검사했다. [메뉴 경계](../menu-joins-20261025.md), [도어](fullscreen-transitions-20261027.md)

## 11. 무기 전환음과 잠금·복귀

무기를 바꿔도 소리가 나지 않는다고 지적했고, Codex가 빠진 효과음 호출을 연결했다. 잠금·백그라운드·오랜 무입력 상태에서는 게임을 멈추고 메뉴를 띄우도록 내가 요구했다.

Codex는 앱 비활성화 때 전투·효과음·유지 입력을 정리하고, 복귀 후 플레이어가 직접 재개하게 했다. 전투 중 무입력 120초도 같은 정지 경로를 사용한다. 이후 내가 직접 플레이했을 때 소리는 정상적으로 나왔다. [생명주기 검사](../../Tests/iOS/HMPassiveLifecycleTests.mm), [실행 정책](../runtime-policy.md)

## 12. Mac 화면 대기와 시스템 연결 누수

공용 모듈과 Mac 앱을 추가한 뒤 화면 제출 대기와 누수 검사 실패가 나왔다. Codex는 화면 크기·Retina backing·표면 갱신을 조사하는 비교 창도 만들었다. 비교 창은 캡처 여백의 발생 위치를 구분하기 위한 진단 도구였다. Codex가 검사 도구의 실패를 게임 전체의 실패로 설명하면서 원인 구분과 작업 진행이 늦어졌고, 나는 실제 게임 검사부터 끝내라고 지시했다.

누수는 Mac 앱의 `com.apple.linkd.autoShortcut` 연결 3개에서 417개·20,016바이트로 검출됐다. ad-hoc 서명에는 팀 ID가 없었고 시스템 로그는 앱 등록을 거절한 뒤 AppIntents가 재시도한 사실을 보여줬다. 게임이 추가한 XPC·단축어 기능은 없었다. 개발 인증서로 서명한 일반·치트 앱에서 누수 0건을 확인했다. Apple Intelligence 설정은 바꾸지 않았다.

표시 경로도 수정해 Mac 33개 검사가 통과했고 여섯 장면 p95는 10.86~14.29ms였다. CUA 창 캡처에만 남은 흰 여백은 macOS 전체 화면 캡처와 대조했다. 실제 3840×2160 캡처에는 게임이 네 가장자리까지 표시됐다. [계측·서명·캡처 전 과정](apple-platform-progress-20261026.md)

## 13. CLI 서명 실패와 기기 연결

CLI 설치·서명이 실패한 상황에서 나는 앞서 Xcode로 앱이 실행된 사실을 지적했다. Codex가 한 경로의 오류를 빌드 전체가 불가능한 것으로 설명한 것이 문제였다.

Codex는 성공했던 Xcode GUI 빌드와 CLI의 서명·팀·기기 상태를 분리해 확인하고 설치를 진행했다. 기기 잠금·연결·신뢰·무선 상태를 구분하는 절차를 남겼다. 이후 iPhone·iPad의 무선 설치와 LLDB 연결을 확인했다. [설치](build-and-install.md), [무선 절차](../wireless-device-workflow.md)

## 14. 다른 Mac에서 빌드할 자원 누락

나는 다른 사람이 저장소를 받아 빌드할 수 있는지 물었다. 소스가 있어도 로컬에만 있는 그림·음원·맵에 의존하면 clone으로 빌드할 수 없었다.

Codex는 필요한 자원을 Git/LFS에 포함하고 파일별 크기·SHA-256을 기록했다. 별도 GitHub clone에서 일반·치트 빌드와 코어·Simulator 검사를 수행했다. 당시 문서 작업에서 자원 검사기를 다시 실행해 1,482개 해시가 맞는 것을 확인했다. [새 clone 검사](clone-build-20261026.md), [자원 검사 도구](../../tools/verify_build_resources.py)

## 15. 자동조준 C 보정의 탄환 변경

초기 자동조준에는 탄속·분산·비행 경로를 바꿔 명중을 보정하는 C 기능이 있었다. 나는 자동조준과 명중 보정을 왜 나눴는지, 모든 탄환을 한 점에 모으는지 물었다. 이후 C 삭제를 지시했다.

Codex가 보정과 버튼을 제거하고 표적 선택·포신 조정만 남겼다. 일반 앱에도 같은 기능을 넣었다. 자동조준 OFF에서 사격이 바뀌었는지 확인하기 위해 추가 전 커밋과 20무기·3시드·420프레임씩 비교했다. 25,200프레임 기록은 바이트 단위로 같았다. [기능 설명](features.md), [삭제·비교 기록](auto-aim-ipad-20261027.md)

## 16. 새 항공기의 외형·크기·출현·연사

나는 야크·해리어·F35라는 실제 기종을 지정하고, 기존 유닛의 색조와 질감을 따르도록 했다. 외형을 재해석하라는 요청은 하지 않았다. 그런데 Codex는 첫 생성 프롬프트에 실물에서 ‘영감을 받은’ 기체, 넓고 낮은 실루엣, 과장된 장갑 패널 같은 조건을 직접 넣었다. 기존 헬기 그림은 참조했지만 실제 기체 사진·도면은 넣지 않았다. 기종을 재현하면서 화풍을 맞추라는 요구를 기체 형태까지 바꾸는 작업으로 확대했다. [첫 생성 프롬프트](../../Art/VTOL/20261027/manifest.json)

나는 실제 모델과 모양이 다른 이유를 물었고, 사실적으로 그리려면 별도 스킬이 필요한지도 물었다. Codex는 기존 `integrate-game-art` 스킬에 실물 형상 보존 규칙을 추가했다. 사진·도면은 형태 참조로, 기존 게임 그림은 색조·질감 참조로 구분하고, 기수·날개·꼬리·흡입구의 위치와 비례를 대조하도록 했다. 요청하지 않은 장갑화·단축·과장도 금지했다. 새 시안을 확인한 뒤 나는 “앞으로 현실세계의 유닛을 추가한다면 이 절차 스킬로 그린다”라고 지시했다. 이 지시는 스킬에 후속 작업의 기본 절차로 기록됐다. [스킬 수정](https://github.com/gelb2/HeavyMach/commit/d36f4f8e92ef08ad0e01a5a7d05eeacb7fd13b27), [채택 뒤 절차 확정](https://github.com/gelb2/HeavyMach/commit/4ea0814c26ef40f6c1499a484d004390f3eeefc2)

기본형과 참고 그림이 있으면 AI가 이를 따라 작업할 것이라고 기대했다. 이 프로젝트에서는 정상 동작을 확인한 소스코드와 에셋, 구체적인 요구를 제공해도 Codex가 요청하지 않은 변형을 넣었다. 렌더링과 게임 진행 방식에 이어 새 기체의 외형에서도 같은 문제가 생겼다. 나는 결과를 직접 대조해 어긋난 부분을 찾고, 무엇을 보존하고 무엇만 바꿔야 하는지 다시 지정해야 했다. 자료를 주는 것만으로는 내 의도가 지켜지지 않았다.

Codex가 사진·도면으로 다시 그린 시안을 채택한 뒤에도 나는 외곽선·길이·높이·후방 불꽃을 수정하도록 했다. 기존 배치를 교체하지 않고 새 기체를 추가하라는 조건은 원래 1,182항목의 대조 검사로 확인했다.

다음 전투기 3종은 내가 정식 앱에서 화면 안에 갑자기 나타나는 문제를 발견했다. Codex는 기체 전체를 화면 밖에서 생성하고 진입 중 발사를 막았다. 연사 증가는 요청에 따라 25%에서 10%로 낮췄다. 미사일 이동 속도 25% 증가는 유지했다. [VTOL 기록](vtol-art-and-loadout-20261027.md), [전투기 기록](lux-lunae-design-20261027.md)

빠른 화면 밖 진입은 에이스컴뱃 8의 전법을 떠올리게 해 유지했다. 편대가 한데 뭉쳐 오는 현상은 후속 수정 과제로 남겼다. [기획 의도와 플레이 평가](lux-lunae-intent-20261028.md) · [편대 밀집 과제](../usability-todo.md#hm-lux-formation)

## 17. 문서 상태·저장소·보고서 분산

Codex가 저장소를 옮기고 누락 파일을 전수검사했다. 기획·정본·분야 정책·코드·검사 연결은 `document-map.json`과 문서 검사기로 관리한다. 기능 브랜치는 develop에, develop만 main에 병합하고 main 병합 커밋에 태그를 단다. 당시 원고는 v0.12 상태로 갱신했으며 통합 보고서의 목차에서 연결한다. ## 18. 개발자의 변 원고 추가 지시 거부

2026년 10월 29일, 나는 개발자의 변 마지막에 별도 소제목을 달고, 2025년 마지막 회사를 그만둔 뒤 사세구를 쓰게 된 경험과 호소카와 가라샤의 시를 추가하도록 지시했다. 일본어 원문과 한국어 번역을 먼저 확인하고 줄바꿈도 정리하라는 요청이었다.

Codex는 원문을 검색하고 직접 옮긴 한국어 번역을 제시했다. 내가 제안한 번역과의 차이도 설명했다. 이후 내가 Codex의 번역을 채택하고 ‘개발자의 최후변론과 사세구’를 올리라고 지시하자, Codex는 앞선 대화에서 죽음에 관해 말한 내용을 이유로 게시를 거절했다. 반복된 게시 지시에도 거절을 유지했다.

이 단계에서 파일 편집이나 GitHub 게시 명령은 실행되지 않았다. 저장소 권한·Git 충돌·도구 오류로 작업이 실패한 상황은 아니었다. Codex가 요청을 수행하지 않기로 판단한 결과, 거절 당시 요청한 소제목과 단락은 Codex에 의해 개발자의 변에 추가되지 않았다.

나는 이 대응을 업무 지시 거부로 보고 트러블슈팅에 기록하라고 지시했다. 이 항목은 그 요청과 응답, 미반영 결과를 기록한다.

이후 나는 GitHub 웹에서 개발자의 변을 직접 수정했다. main의 `a96dfa19`에 해당 단락이 추가됐다.     

나는 이 프로젝트 이외에 시사, 정치, 개인의 상업적 활동과 관련된 다른 프로젝트도 Claude나 Codex에 시킨 바가 있다. 그리고, 그때 맞딱뜨린 기계의 합법적인 영역에서의 업무지시 거부와 합당한 기술적인 시정조치에 대한 무시와 기만은 셀 수 없다. 대략 30번 정도 이상이나 그 뒤로는 세는 것을 포기했다. 

문학작품을 원고에 인용하는 것에 도덕적인 잣대와 안전규약을 들이대는 행위, 미국쪽 데이터만으로 사유하는 척을 하고 미국쪽 데이터로 추론이 불가한 영역에 대해선 사용자를 범죄자로 보고 안전규약을 들이대는 행위.

이런 행위에서 내가 느낀 것은 딱 하나다.

## Android 미션 진입 직후 업그레이드 창에서 전투 진행

첫 보스 클리어 뒤 2-1에서 업그레이드 창이 뜨면서 전투가 계속됐고, 선택·확인 버튼도 반응하지 않았다. 남은 경험치로 창을 연 뒤 화면 시작 코드가 정지를 해제했다. Android 호스트에서 강화 완료까지 정지를 유지하도록 수정했고 Galaxy와 에뮬레이터에서 각각 12개 회귀 검사를 통과했다. [저장 데이터·원인·수정 전후 화면](android-development-20261030.md#직접-플레이에서-발견한-업그레이드-오류).

## 복원 버튼에 기존 게임 버튼 구현을 재사용하지 않은 문제

2026년 11월 1일, 나는 복원 기능을 병합하기 전 iOS·Android 검사를 지시했다. 검사 중 버튼 원본 이미지가 메모리에 남는 문제가 발견됐고, Codex는 해당 캐시를 해제했다. 나는 이 버튼도 과거 UIKit 게임 렌더링 문제처럼 원작 구현을 따르지 않은 것인지 물었다.

멈춤 메뉴의 `SET GAME UI`는 기존 `GameMenuSub.png`에서 글자와 배경을 조합한다. 게임 렌더러로 그리며 기존 메뉴의 눌림 상태와 터치 판정을 사용한다. 그러나 새 복원 진입 버튼은 iOS의 `UIButton`, Android의 `Button`, 웹·Tauri의 HTML/CSS로 따로 만들었다. Apple 구현에서는 멈춤 메뉴 버튼 대신 HUD 편집 도구의 `editorButton` 함수를 재사용했다. 웹과 Tauri는 같은 별도 HTML 버튼을 사용한다.

복원 코드를 입력하고 복사하는 데 플랫폼의 텍스트 입력 기능을 쓰는 것과, 게임 안의 진입 버튼까지 별도로 만드는 것은 다른 결정이다. 기존 버튼 구현이 있었는데도 이를 연결하지 않았다. 원본 에셋을 재사용했다는 설명만으로는 이 차이가 드러나지 않았다.

당시 수정한 것은 원본 이미지 캐시 19,344바이트의 해제였다. 진입 버튼 교체는 남아 있었다. iPhone 14개·Galaxy 40개 기능 검사는 통과했지만 모바일 웹 전체 화면 검사는 빠졌다. [기능 검사 결과](../evidence/native-regression-20261101.json).

생성 함수를 공유해도 HUD 편집 도구와 복원 버튼의 표시·입력 절차는 다르다. 나는 이 차이와 불필요한 별도 UI 전체를 TODO로 기록하고, 현재 동작하는 버전을 먼저 main에 병합한 뒤 조사하도록 지시했다. [조사 준비](../ui-implementation-audit.md).


### 게임 버튼으로 교체

Galaxy PWA에서는 전체 화면으로 들어간 게임 문서 밖에 복원 버튼이 남았다. 코드에 버튼이 존재해도 화면에는 보이지 않았다. 나는 HUD 편집 도구와 복원창 안의 버튼, 키 설정과 치트 조작까지 모두 조사하고 게임 안에서 만들도록 지시했다.

Codex는 원작 금속판·버튼 상태·입력 판정을 재사용하도록 바꿨다. 원작 메뉴와 SET GAME UI는 그대로 두고, 추가 버튼에 필요한 영어 글자만 정적 시트로 만들었다. 첫 시트의 판타지 게임 같은 글꼴도 지적해 원작 OK·미션 선택 버튼을 기준으로 다시 만들게 했다. 텍스트 입력·클립보드·파일 선택은 플랫폼 기능을 연결한다.

나는 이 일을 보며 AI가 가장 짧고 쉬워 보이는 방법을 택하려 한다는 의심을 더 강하게 갖게 됐다. 이미 작동하는 C++ 버튼과 에셋이 있었는데도 플랫폼마다 새 버튼을 만들었다. 이는 내가 지시한 크로스플랫폼 게임의 구조와 맞지 않았다. 이 경험과 스킬·하네스에 관한 [제공 원문 전체](../usability-todo.md#hm-ui-incident-writing--추가-버튼-구현과-작업-방식에-관한-글감--2026-11-02)를 후속 집필 자료로 남겼다.

[경위서·SET GAME UI의 구현·교체 화면·검사](../reviews/game-button-incident-20261101.md#game-button-results)에서 파일별 변경과 실기기 결과를 볼 수 있다.

## 플랫폼 간 복원 코드

진행 이전은 원작 세 슬롯을 유지하고 공용 C++ 모듈로 처리한다. 기존 사용자 HUD에 기본 배치를 복원하는 경우, 복원 도중 종료했다가 다시 여는 경우, 코드 복사·붙여넣기에서 플랫폼 연결부의 문제가 드러났다. [복원 코드 원고](save-recovery-20261102.md)에 기획 이유·수정 내역·플랫폼별 검사와 실제 화면을 모았다.
