# 카모프 헬기·럭스루나에 유로파이터 개발 계획 — 2026-11-09

신규 유닛 핫픽스를 main `4bbb3f50`에 배포한 뒤, 개발자는 구현 절차 준수를 확인할 다음 과제로 **러시아제 카모프 헬기**와 **럭스루나에 유로파이터** 2종을 지정했다. 이번 기록의 범위는 개발 계획과 TODO다. 그림 생성, 게임 데이터 추가, 코드 구현과 실제 배치는 시작하지 않았다.

## 두 유닛의 범위

| 대상 | 지정된 내용 | 설계에서 확정할 내용 | 공통 경로의 기준 |
|---|---|---|---|
| 카모프 헬기 | 러시아제 카모프 계열 헬기 1종 | 정확한 형식, 원작 대비 표시 크기, 부품 분리·연결점, 무장·역할·등장 위치 | 원작 헬기의 MCH 정의·파츠·회전익 표시·이동·무장·피격 경로 |
| 럭스루나에 유로파이터 | 럭스루나에 계열 유로파이터 1종 | 기존 계열과 공유할 도장·표식, 원작 대비 크기, 무장과 편대·증원 배치 | 원작 항공기와 핫픽스 후 Lux의 공통 MCH 파츠·HMEX 속성·편대 경로 |

카모프의 구체적인 형식과 두 유닛의 수치·배치는 아직 지정되지 않았다. 이 표의 설계 항목을 이미 합의된 기능이나 수치로 취급하지 않는다. 기존 럭스루나에의 증원 수·시점이나 전체 캠페인 배치를 계획 문서만으로 바꾸지 않는다.

## 제작·연결 순서와 산출물

1. **기존 유닛을 기준으로 정의한다.** 원작 헬기·항공기의 실제 MCH 레코드, 파츠 트리, 소켓·총구, 무장·AI·피격 범위를 추출해 이름과 원본 SHA를 기록한다. 두 유닛의 역할·크기·배치는 이 기준과 연결한 설계 표로 남긴다. 원작 소스나 제작 도구를 확보했다고 표현하지 않는다.
2. **그림을 만들기 전에 참조를 고정한다.** HeavyMach1의 실제 원작 그림을 계열별 최소 3개 골라 캔버스, 알파 범위, 팔레트, 층 순서와 게임 배율을 기록한다. 실물 외형 자료와 원작 미술 참조를 구분한다. 새로 만든 전투기나 탈락 시안을 원작 그림으로 사용하지 않는다. 유로파이터의 Lux 도장·표식은 기존 승인본과 별도로 대조한다.
3. **부품별 원본과 채택본을 보존한다.** 원작 시점·도트 크기·색·명암을 기준으로 몸체와 움직이는 부품을 만든다. 회전하는 부품을 몸체에 고정해서 그리지 않는다. 생성 입력·출력, 채택·탈락 구분과 SHA를 남긴다. 게임에 맞추려고 X/Y를 따로 늘리거나 충돌·사거리 수치를 바꾸지 않는다.
4. **실행용 파일을 오프라인으로 만든다.** 기존 `prepare_unit_images`와 실행용 manifest를 확장해 실제 파일을 내보낸다. 표준 PNG의 알파·크기·프레임·연결점을 확인하고 Apple·Android·Web별 공통 디코딩 결과와 업로드 입력 바이트를 대조한다. 이름만 등록한 가상 파일, 실행 중 기종별 crop·축소를 추가하지 않는다. 미채택 그림은 배포에서 제외한다.
5. **정의는 데이터로 등록한다.** `prepare_unit_data_authoring.json`과 기존 내보내기를 통해 MCH의 무장·파츠·기체 레코드를 만들고 같은 파서로 읽는다. 기존 `prepare_unit_data_baseline.cpp`는 과거 핫픽스 기준을 추출한 도구이며 새 유닛 공장으로 재사용하지 않는다. 새 C++ factory를 만든 뒤 JSON으로 포장하는 우회를 금지한다. 원작 보관 파일과 기존 레코드의 바이트를 유지한다.
6. **공통 소비 경로에 연결한다.** 실제 파츠 트리와 소켓을 통해 몸체·회전익·분사·무장을 표시하고, 공통 이동·사격·탄환·충돌·피격·저장 경로를 사용한다. 필요한 동작이 기존 데이터·HMEX로 표현되는지 먼저 확인한다. 표현할 수 없는 동작은 필요한 필드·소비자·회귀 범위를 설계에 추가한 뒤 공통 계약으로 구현한다. 기체 이름별 직접 draw나 플랫폼별 AI 복제는 추가하지 않는다.
7. **검증 앱에서 먼저 조립·전투를 확인한다.** 기존 유닛과 두 신규 유닛을 함께 배치해 실제 크기, 접합·회전·방향 전환·이동·사격·피격·파괴를 확인한다. 검증 생성과 캠페인 배치를 구분하고, 확정된 배치만 MAP 또는 공통 편대 데이터로 반영한다.
8. **검토 후 정식 빌드를 배포한다.** 독립 검토에서 입력 그림→변환 파일→패키지→파서→파츠·전투 소비자를 추적한다. 작업 브랜치→develop→main을 지키고, 검사한 제품 파일과 배포 파일의 해시를 비교한다. 기존 사용자 저장·원본·태그를 보존한다.

현재 아이폰은 일반 빌드만 설치하고 Android·PWA·Tauri 치트 빌드로 검사한다는 최신 지시를 기준으로 계획했다. 이후 검사 환경이 바뀌면 실제 수행한 대상과 범위를 별도로 기록한다. 전체 무기 발사를 모든 무기가 모든 표적에 명중했다는 결과로 확대하지 않는다.

## 작업 위치와 보존

구현 착수 시 최신 develop에서 `feat/kamov-lux-eurofighter` 작업 브랜치를 만든다. 지금은 그 구현 브랜치를 만들지 않았다. 제작 원본은 기존 `Art/Extensions` 규칙, 실행용 파일은 `Resources/RuntimeImages`·`RuntimeData`, 공통 파서는 `Sources/Core`, 플랫폼 연결은 각 기존 호스트를 따른다. 원작 이미지·RawData와 사용자 저장은 수정하지 않는다. 새 유닛 제작 때문에 게임 규칙·좌표계·저장 시점·전체 캠페인 난도를 임의로 바꾸지 않는다.
