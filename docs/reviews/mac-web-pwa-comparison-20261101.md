## 공통 복원 코드 작업 순서

2026-11-01 최신 계획. 기존 목록의 **6번 저장 보존과 7번 복원 코드**를 하나의 기능으로 설계하고, **4번 저장·복구 검사**를 거쳐 배포를 판단한다. iOS·iPadOS·네이티브 Mac·Android·순수 웹/PWA·Tauri가 같은 코드 규격과 생성·복원 모듈을 사용한다. 공용 게임 코어는 유지한다. `feat/save-transfer`에서 공통 모듈과 플랫폼 연결을 구현 중이다.

### 아이폰 저장으로 복원 검사 — 2026-11-01

아이폰의 기존 저장과 설정을 별도로 백업했다. 레벨 19, 경험치 221,706, 무기 14종이 있는 두 번째 슬롯이다. 세 슬롯 전체와 HUD 위치·키 배치·조준 설정을 하나의 복원 코드로 옮겼다. 원본 저장과 복원 코드는 로컬 검사 폴더에 보관한다.

아이패드 검사 중 전투 화면에 `SET GAME UI`가 나타났다. 저장한 HUD 배치가 화면 크기 때문에 겹칠 때 별도 편집 버튼을 띄우던 코드였다. Apple·Android에서 이 버튼을 숨겼다. iPad에서 전투 중 숨김과 일시정지 메뉴의 편집 진입을 직접 확인했다.

갤럭시 첫 복원에서는 기본 위치인 HUD 부품에 기존 사용자 지정 위치가 메모리에서 남았다. 기본 위치도 지우고 적용하도록 Android 설정 읽기를 수정했다. 기존 갤럭시 배치를 다시 넣고 같은 아이폰 코드를 복원했을 때 설정 전체가 일치했고 대기 파일도 지워졌다.

Tauri에서는 복원 파일 명령의 앱 권한 선언과 복원 화면 모듈의 URL 해석을 수정했다. `tauri://` 페이지 주소를 기준으로 모듈 경로를 만들자 슬롯 화면에 버튼이 표시됐고 복원이 완료됐다.

남은 직접 검사는 Galaxy의 입력창을 통한 복원과 전투, Tauri 복원 후 전투·앱 재시작, 최신 네이티브 Mac 빌드의 전투, iPhone 앱의 코드 생성이다. 검사 도중 Mac이 잠겼고 iPhone 연결도 끊겼다. 단계별 강제 종료·용량 부족 검사와 공개 PWA 배포도 남았다. [검사 기록](../evidence/save-transfer-slots-20261101.json).

### 세이브 슬롯 화면으로 진입 제한 — 2026-11-01

사용자 지시에 따라 코드 생성·입력을 세이브 슬롯 선택 화면으로 옮겼다. 전투 중 상태를 추출하던 웹 함수를 제거하고, Apple·Android의 코드 생성에서 일시정지·추가 저장 호출을 제거했다. 기존 저장 절차가 끝난 세 슬롯을 읽는다. 버튼은 기존 OK 버튼을 가리지 않도록 우측 상단에 배치했다.

웹에서 타이틀·모드 선택·미션 선택·전투·일시정지의 버튼 숨김, 슬롯 화면의 버튼 표시, 코드 생성 전후 저장 파일 일치, native 코드의 웹 복원을 확인했다. 복원은 슬롯 화면에서 확인한 뒤 게임 페이지를 닫고 적용한다.

Web·Android 치트·Mac 치트·iOS arm64 시뮬레이터 치트 빌드는 통과했다. 공통 모듈의 native/Wasm 코드 일치와 손상·잘림·슬롯 복사·복구 중단 검사도 통과했다. 위 실기기 검사로 Apple·Android·Tauri의 저장값 대조를 추가했다. 남은 화면 검사와 복원 단계별 강제 종료·용량 부족 검사를 마친 뒤 배포한다. 공개 웹에는 아직 이번 기능을 올리지 않았다.

### 1. 작업 기준과 변경 범위 확정

`feat/tauri-mac`의 `e433d8ba`에서 `feat/save-transfer`를 분기했다. 아직 main에 없는 Tauri 실행기와 웹 배포 코드를 그대로 이어받는다. 작업 전 원격 main의 사용자 문서 변경과 기존 보호 해시를 확인한다.

새 코드는 `Modules/SaveTransfer/`에 둔다. 기존 `Sources/Core`의 전투·탄도·스폰·경험치·강화·저장 형식은 바꾸지 않는다. Apple·Android·웹 호스트에는 화면·현재 진행 읽기·저장 적용을 연결하는 데 필요한 부분만 추가한다. 각 파일과 변경 이유를 목록으로 남겨 기존 보호 목록과 대조한다. 이 연결부와 수동 조준점 숨김은 최신 사용자 요구에 따른 변경 범위다. 나머지 기여자 웹 코드와 기존 플랫폼 파일은 보호한다.

### 2. 저장 항목과 코드 형식 확정

기존 3슬롯 진행 전체, 무기와 순서·탄약, 경험치·미션·강화, HUD·키·조준 설정을 조사표에 연결한다. 슬롯 단위 가져오기에서는 다른 슬롯을 유지한다. 모든 슬롯 복구는 별도 선택으로 제공한다. 미지정 HUD·키 설정과 사용자가 지정한 설정을 구분한다.

코드는 `HM1-` 접두부, 형식 버전·게임 데이터 호환 정보·선택 범위·진행·설정·손상 검사값을 포함한다. 고정 순서 직렬화·압축·Base64url 변환을 사용한다. 암호화·salt는 넣지 않는다. 공통 구현에서 길이·형식·손상·값 범위를 검사한다. 코드 호환 버전과 출시 버전을 분리해 단순 앱 업데이트로 기존 코드가 무효가 되지 않게 한다.

초기·중간·최종 진행, 모든 무기·탄약, 설정 변경 상태로 코드 길이를 측정한다. 복사·붙여넣기와 같은 내용을 담은 파일 저장·불러오기를 기본으로 한다. 코드는 생성한 시점의 진행을 담는다.

### 3. 생성·복원 공통 모듈 구현

`Modules/SaveTransfer/`의 같은 C++ 구현을 Apple·Android에서 네이티브로 빌드하고, 웹·Tauri에서는 별도 Wasm 모듈로 빌드한다. 웹 게임의 기존 Wasm에 복원 로직을 각각 다시 작성하지 않는다. 압축·해석·검증·슬롯 선택·복원 적용 계획은 이 공통 모듈이 담당한다. 테스트 데이터도 공용으로 둔다.

플랫폼 연결부는 정해진 인터페이스로 현재 진행 읽기, 파일·설정 쓰기, 복구 기록 보관, UI·클립보드·파일 선택을 제공한다. 복원 순서는 공통 상태 처리에서 결정한다. 플랫폼마다 별도의 검증 규칙이나 예외를 늘리지 않는다.

생성은 **세이브 슬롯 선택 화면 → 기존 저장 완료 확인 → 저장된 세 슬롯과 설정 읽기 → 공통 모듈에서 코드 생성 → 복사/파일 출력** 순서다. 전투·일시정지 화면에는 생성 버튼을 두지 않는다. 생성 때문에 게임을 중단하거나 진행 값을 별도로 파일에 쓰지 않는다.

복원은 **코드 해석·검증 → 진행 요약·대상 슬롯 확인 → 기존 진행 보관 → 복구 기록 작성 → 진행·설정 적용 → 다시 읽어 대조 → 완료 기록 → 게임 다시 열기** 순서다. 중간에 종료되면 다음 실행에서 복구를 마친 뒤 게임을 연다. 플랫폼이 여러 저장소를 사용하므로 단일 파일 교체만으로 완료하지 않고 진행과 설정을 함께 검사한다.

### 4. 플랫폼 UI 연결과 저장 보존 보완

2026-11-01 후속 지시에 따라 **세이브 슬롯 선택 화면에서만** 코드 만들기·넣기를 연다. 타이틀·모드 선택·미션 선택·전투·일시정지·HUD 편집 화면에서는 숨기며 호출도 거부한다. 웹·Tauri의 복원 적용은 확인 후 게임 페이지를 닫고 실행기에서 처리한다. 버튼은 원작 메뉴 에셋과 영문 표현을 따른다.

Tauri는 기존 OS 자동 백업을 유지한다. 전체 삭제와 DB·설정 중 일부 삭제를 구분하고, 부분 삭제 상태로 정상 백업을 교체하지 않도록 보완한다. 웹/PWA는 사이트 데이터가 삭제되어도 외부에 보관한 코드나 파일로 복구한다. 서버·iCloud 없이 동작하도록 구현한다. 코드나 파일이 생성된 이후의 추가 진행은 새 코드에 담는다.

HUD는 그룹 ID·정규화 좌표를 공통으로 전달한다. 적용 화면의 안전 영역과 버튼 터치 영역을 함께 계산한다. 지원하지 않는 입력 설정은 원본 값을 보관하고 해당 기기에서 사용할 수 있는 설정을 적용한다. 기기를 다시 옮겼을 때 설정이 사라지지 않는지도 검사한다.

### 5. 수동 조준점 숨김과 화면 확인

웹 호스트의 `drawKeyboardIndicators()`에서 수동 조준점을 그리는 분기만 숨긴다. 같은 웹 게임을 사용하는 Tauri에도 반영한다. 메뉴 포커스, 방향키가 바꾸는 조준 좌표, 트랙패드 사격, 자동조준 표시는 유지한다. iPad 키보드·트랙패드와 Mac 키보드에서 확인한다.

iPad Safari 상단 직선도 이 화면 검사에서 재현·출처를 확인한다. 실제 기기에서 재현되지 않으면 미확인 상태로 남기고, 입력이나 화면 내용을 가리는 문제가 확인되면 배포 전에 수정한다.

### 6. 공통·교차 플랫폼 검사

먼저 공통 모듈의 native·Wasm 결과를 비교한다. 동일한 스냅샷에서 같은 코드를 만들고, 다시 해석하면 같은 진행과 설정이 나와야 한다. 코드 길이·호환 버전·잘못된 입력도 함께 검사한다.

각 플랫폼이 만든 코드를 다른 플랫폼 모두에서 읽는 조합을 검사한다. iOS·Android·웹/PWA·Tauri의 왕복 이동을 기본으로 하고 iPad·네이티브 Mac의 설정·화면 차이를 포함한다. 각 수신 기기에서 경험치·해금 미션·무기 순서·탄약·부품 단계·실제 외형·HUD 위치와 터치 판정·키·조준 모드를 확인한다. 이어서 플레이해 새 코드를 만들고 원래 기기로 가져온다. 설정 차이 때문에 코드가 달라졌다면 필드별 차이를 확인한다.

새 모듈을 사용하지 않는 기존 플레이도 검사한다. 기존 저장 읽기, 이동·점프·수동/자동 사격·무기 전환·미션 클리어·강화·종료·재실행을 확인하고, 보호 코어와 자원의 해시를 대조한다. 실제 기기와 시뮬레이터·에뮬레이터 결과를 각각 기록한다.

### 7. 4번 저장·복구 실패 검사

잘린 코드·손상·지원하지 않는 버전·잘못된 무기·수치·과도한 압축 해제 크기를 거부하고 현재 진행이 유지되는지 확인한다. 가져오기 중 종료·디스크/브라우저 용량 부족·중복 실행·종료 직전 백업 오류·업데이트·새 프로필 가져오기를 시험한다. 캐시만 삭제, DB만 삭제, 설정만 삭제, 전체 사이트/웹뷰 데이터 삭제 후의 복구도 각각 확인한다.

오프라인 플레이→코드 생성→완전 종료→다른 기기 복원, 웹 데이터 삭제→외부 코드 복원 절차를 검사한다. 서로 다르게 진행한 저장은 요약을 비교해 선택하고 수치의 자동 합산은 하지 않는다. 같은 코드를 다시 넣어도 무기·탄약이 중복 지급되지 않아야 한다.

### 8. 배포

공통 기능·교차 복원·실패 검사를 통과하면 결과와 남은 문제를 보고한다. 이후 `feat/save-transfer`를 기존 Tauri 작업에 합치고 develop→main 순서로 병합한다. 원격 main에서 사용자가 고친 문서와 기여자의 원본 커밋을 확인한다. 새 태그·릴리스 노트·국영문 설치/복원 안내를 갱신하고 웹/PWA와 플랫폼별 빌드를 배포한다.

Tauri Mac의 DMG·배포 서명·공증 준비 상태는 별도로 표시한다. 웹 게시, Mac 로컬 빌드, 서명된 공개 설치본을 각각 확인한다. Windows는 같은 Tauri 프로젝트의 설치본 빌드를 다음 단계로 진행하고 실제 실행 검사는 해당 환경이 준비된 뒤 수행한다.

### 후속 과제

- **2번 권한·음향:** PWA 재실행 시 동작 권한, 잠금·백그라운드 복귀·AirPods 연결 변경. 현재 플레이에서 동작한 범위를 유지하며 후속 조사한다.
- **3번 Mac 비교:** 같은 저장으로 30분 실행, 전체 프로세스 메모리·긴 프레임·시작 시간·음향·백업 쓰기 횟수 비교. 저장·종료 실패가 발견되면 7단계에서 먼저 수정한다.
- **모바일 나머지 검사:** 브라우저/PWA 설치 전후 진행 공유와 각 플랫폼 설치 안내. 이번 코드 복원·회전·HUD·재실행에 영향을 주는 검사는 6~7단계에 포함한다.
- **Windows:** x64 설치본·WebView2 구성·해시·로그, 이후 실제 설치·플레이·저장·업데이트·서명 검사.

## 서버 없는 복원 코드와 플랫폼 간 진행 이동

2026-11-01 추가 지시: 고전게임의 패스워드 세이브처럼 진행 데이터를 코드에 담고, 다른 기기의 앱·PWA에서 그 코드를 입력해 복원하는 방법을 6번 백업·영속성 과제와 연결한다. 사용자 전제는 싱글플레이 게임이며, 경험치·미션 진행·무기 순서·탄약·부품 강화 등은 게임이 해석할 수 있는 값이라는 것이다. 후속 지시에 따라 **암호화와 salt는 넣지 않고 손상 검사와 값 검증을 사용한다.** 이번 결과는 소스 조사와 설계이며 기능 구현·플랫폼 간 실행 검사는 아직이다.

### 가능한 이유와 복원 범위

이 방식은 가능하다. Mega Man 2의 공식 설명서도 현재 진행을 패스워드로 표시하고 다음 실행에서 입력해 획득 무기·아이템과 함께 이어 하는 절차를 설명한다. 다만 이 사례가 전투 중 모든 상태를 저장했다는 뜻은 아니다. HeavyMach은 필요한 진행 항목을 직접 정의하고 빠짐없이 직렬화한다. [공식 설명서, Password 절](https://www.nintendo.co.jp/clv/manuals/en/pdf/CLV-P-NABBE_en.pdf).

원작과 복원판의 에셋은 기체·무기·미션을 재구성하는 재료다. **어떤 것을 얻었고 얼마나 남았는지 나타내는 사용자의 값은 복원 코드에 들어 있어야 한다.** 기기 ID나 짧은 해시만으로는 이 값을 재생할 수 없다. 암호학적 해시는 원래 데이터를 되찾는 용도가 아니며, 이 설계에서는 코드의 내용이 손상됐는지 확인하는 데만 쓴다. [NIST 해시 정의](https://csrc.nist.gov/glossary/term/hash_function).

현재 소스에서 확인한 기반은 다음과 같다.

| 데이터 | 실제 저장·소비 코드 | 이식 방법 |
|---|---|---|
| 세 슬롯의 진행 | `Sources/Core/SaveData.hpp/.cpp`: 슬롯당 1,208바이트, 전체 3,624바이트, 명시적 little-endian | 초기 형식은 기존 저장 바이트 전체를 담아 알 수 없는 필드도 누락하지 않는다. |
| 경험치·레벨·무기 순서·탄약 | `SaveSlot`의 경험치·레벨 필드와 순서가 있는 무기 레코드 | 값과 순서를 그대로 보존하고 사용 가능한 무기 이름·범위를 검사한다. |
| 미션 진척·부품 강화·외형 | `GlobalInfo::updateLastStage`, `GameSession::gradeName`·`playerPart` | 진행 필드와 부품 단계로 기존 게임 코드가 외형을 다시 조립한다. 이미지 자체를 코드에 담을 필요는 없다. |
| Apple 진행 저장 | `HMGameView.mm`가 공용 `SaveData::decode/encode` 사용 | 앱의 가져오기·내보내기 연결을 추가한다. |
| Android 진행 저장 | `Runtime.cpp`가 같은 공용 `SaveData` 사용 | 앱의 저장 경로와 원자적 파일 교체에 연결한다. |
| Web·Tauri 진행 저장 | `WebGameView.cpp`가 같은 공용 형식 사용, Tauri는 이를 백업 | 게임 진입 전 기존 저장소에 적용하고 저장 대기열과 충돌하지 않게 한다. |
| HUD·키·조준 설정 | Apple JSON·NSUserDefaults, Android `HUDLayoutV1.txt`·`InputV1.txt`, 웹 JSON·localStorage | 공통 설정 형식으로 내보내고 각 플랫폼 형식으로 적용한다. HUD의 정규화 좌표·그룹 ID를 보존하고 화면 크기에 맞는 배치를 검증한다. |

복원 범위는 기존 저장 절차를 마친 세 슬롯의 진행과 사용자 설정이다. 세이브 슬롯 선택 화면에서 코드를 만든다. 전투 도중의 탄환·적 위치·난수·탄약 캐시를 추출하는 처리는 넣지 않는다.

### 코드 구성과 사용 흐름

기본안은 `HM1-` 접두부 뒤에 **형식 버전·게임 데이터 호환 버전·진행·설정·손상 검사값**을 담는 것이다. 고정 필드 순서로 직렬화하고 압축한 다음 Base64url 같은 텍스트로 표현한다. 체크섬 또는 SHA-256은 오타·누락·손상 검출에 쓰며 암호화나 위조 방지로 설명하지 않는다. salt·비밀키·기기별 암호는 필요 없다. [Base64url 표준](https://www.rfc-editor.org/rfc/rfc4648.html#section-5).

3,624바이트 전체 진행을 압축 없이 Base64로 표현하면 4,832자다. 설정·헤더·검사값은 별도로 늘어난다. 실제 압축 길이는 초기·중간·완료·전체 무기 상태를 만들어 측정한다. 짧은 숫자 몇 자리로 모든 상태를 담을 수 있다고 가정하지 않는다. 복사·붙여넣기를 기본으로 하고 같은 내용의 파일 저장·불러오기도 제공하는 안이다. QR은 길이를 측정한 뒤 추가 여부를 정한다.

1. 기기 A에서 복원 코드 만들기 → 현재 진행을 고정해 코드 생성 → 복사 또는 파일로 보관.
2. 기기 B에서 코드 넣기 → 형식·길이·손상·값·게임 버전 검사 → 미션·경험치·무기 요약 표시.
3. 기존 진행을 별도 보관하고 적용할 슬롯을 선택 → 진행과 설정을 함께 적용 → 재실행 후 확인.
4. B에서 더 플레이한 뒤 새 코드를 생성해 A로 가져온다. 이전 코드는 생성 당시의 진행으로 남는다.

이것은 **사용자가 전달하는 시점의 진행 이동**이다. 두 기기가 서로 다른 곳에서 계속 플레이하면 최신 상태를 자동으로 알 수 없다. 복원 전 두 진행을 비교하고 하나를 선택한다. 경험치·미션·탄약의 최댓값을 항목별로 합치면 소비한 탄약이 되살아나는 등 다른 상태가 만들어지므로 자동 합산하지 않는다. 코드를 브라우저 밖에 보관했다면 사이트 데이터 삭제 후에도 그 시점으로 복원할 수 있다. 코드를 만들기 전의 변경이나 코드와 저장을 모두 잃은 상태까지 복구하지는 못한다.

### 모듈·검증 계획

공용 코어의 전투·탄도·경험치 계산은 유지한다. 새 복원 형식과 변환은 별도 모듈로 만들고 기존 `SaveData`를 읽는다. 공통 테스트 데이터로 C++과 웹 측 결과를 대조한다. 모든 플랫폼에 코드 입력·출력 화면과 저장 연결을 넣으려면 Apple·Android·웹 호스트의 제한된 변경은 필요하다. 현재 보존 대상 파일을 변경하는 범위는 구현 계획에서 파일별로 제시한다. Tauri 외부 실행기만으로 네이티브 앱에 새 메뉴가 생긴다고 보지 않는다.

- 형식 검사: 직렬화→코드→복원 후 진행 바이트·설정 일치. 잘림·오타·손상·지원하지 않는 버전·잘못된 미션·무기·탄약·과도한 압축 해제 크기를 처리한다.
- 교차 검사: Apple 네이티브·Android·Tauri·웹/PWA가 각각 만든 코드를 다른 대상이 읽고 다시 내보낸 결과를 공통 기준과 비교한다. iPhone·iPad·Mac의 화면비와 HUD도 따로 확인한다.
- 실제 기능 검사: 경험치·미션 해금·무기 순서·각 탄약·부품 단계·외형·HUD 위치와 터치 판정·키·자동조준을 확인한다. 종료·재실행 뒤에도 같은 진행인지 검사한다.
- 실패 검사: 가져오기 중 강제 종료, 공간 부족, 기존 진행과 충돌, 같은 코드 반복 입력, 사이트 데이터 삭제 후 코드 복구. 실패 때 기존 진행과 복원 전 사본을 유지한다.
- 저장 범위 검사: 현재 메모리와 마지막 디스크 저장이 다른 상태에서 코드를 만들고 표시한 시점의 값이 담기는지 확인한다. 가져오기 적용은 게임 진행을 멈춘 상태에서 처리한다.

공용 형식과 에뮬레이터·시뮬레이터·Mac·브라우저 검사는 구현 후 자동화할 수 있다. 연결된 실기기에서는 실제 입력·클립보드·파일 선택·재실행을 추가 검사한다. Windows는 해당 빌드·실행 환경이 준비된 뒤 포함한다. **현재는 가능성과 시험 방법을 조사한 상태이며, 플랫폼 간 복원이 통과한 상태는 아니다.**

6번의 서버 없는 외부 보관 수단에 이 복원 코드를 추가하고 7번과 함께 설계한다. Tauri의 OS 자동 백업은 유지한다. 서버 자동 동기화 구축은 이 코드 방식의 전제 조건에서 제외한다. 보고서 검토 후 구현·4번 검사·배포 판단 순서는 유지한다.

## 웹 데이터 삭제 후 저장 보존 조사와 배포 순서

2026-11-01 최신 지시: **6번 저장 보존 조사·계획 → 보고서 검토 → 6번 구현과 4번 저장·복구 검사 → 배포 판단** 순서로 진행한다. 이번 작업은 코드 조사와 계획 작성이다. 아래 새 기능과 삭제 조건별 검사는 아직 실행하지 않았다.

### 조사 결과

Tauri는 웹뷰와 별도로 OS 파일에 진행을 보관할 수 있다. 현재 `Application Support/com.gelb2.heavymach.desktop/saves/`에 정상 백업 두 세대를 저장한다. 앱의 고정 WKWebView 저장소와 별개다. 웹뷰 데이터를 비운 뒤 OS 백업으로 슬롯을 복구한 기존 검사도 있다.

순수 웹·PWA는 사이트 데이터 전체 삭제에 대비해 **브라우저 밖에 사본을 남겨야 한다.** IndexedDB, localStorage, Cache Storage, OPFS는 모두 브라우저가 관리한다. PWA 설치와 `navigator.storage.persist()`는 사용자가 사이트 데이터를 삭제한 뒤의 복구 수단이 아니다. WHATWG 저장 표준은 지속 저장도 사용자의 삭제를 허용하며, WebKit은 자동 제거와 사용자 삭제를 구분한다. [저장 표준](https://storage.spec.whatwg.org/#user-interface-guidelines) · [WebKit 저장 정책](https://webkit.org/blog/14403/updates-to-storage-policy/).

| 삭제 범위 | Tauri Mac | 순수 웹·PWA |
|---|---|---|
| 일반 HTTP 캐시·게임 다운로드 캐시만 삭제 | OS 백업과 웹 저장은 별개다. 실제 캐시 삭제 메뉴가 지우는 범위를 검사한다. | 진행 DB를 함께 지우지 않았다면 진행을 유지하고 게임 자원을 다시 받을 수 있다. |
| IndexedDB만 삭제 또는 localStorage만 삭제 | 일부 데이터만 남는 조건을 추가 처리해야 한다. 아래 코드 조사 결과를 따른다. | 남아 있는 데이터와 외부 사본을 대조해 복원해야 한다. |
| 웹뷰 또는 사이트 데이터 전체 삭제 | OS 백업이 남으면 시작 전에 복구한다. | 브라우저 내부 사본도 함께 사라진다. 외부 파일 또는 서버 사본으로 복구해야 한다. |
| 브라우저 프로필 삭제·새 프로필 사용 | 해당 Tauri OS 백업과는 별개다. | 외부 사본과 이를 다시 찾을 수단이 필요하다. |
| 앱의 Application Support 폴더까지 삭제 | OS 백업도 사라진다. 사용자 내보내기나 외부 저장본이 필요하다. | 해당 없음. |

위 표는 구조와 표준에 따른 판단이다. 기기별 설정 화면의 ‘캐시 삭제’가 실제로 무엇을 지우는지는 별도 검사한다. 게임 자원 캐시를 지운 뒤에는 오프라인 상태에서 게임을 다시 내려받을 수 없으므로, 진행 보존과 오프라인 실행 가능 여부도 각각 기록한다.

### 현재 코드에서 찾은 보완점

`Desktop/Tauri/frontend/storage.js`의 `empty()`는 DB와 설정이 **모두 비었을 때만** 참이다. `boot.js`도 이 조건 또는 복구 중단 기록이 있을 때 자동 복구한다. 따라서 DB만 지우고 키·조준 설정이 남았거나, 설정만 지우고 게임 데이터가 남은 경우에는 자동 복구가 시작되지 않는다. 코드 조사로 확인했으며 실제 삭제 재현은 다음 검사에 포함한다.

이 상태로 새 게임을 시작하면 뒤의 주기적 백업이 부분 삭제 상태를 받아들일 가능성도 있다. 두 세대 백업만으로 이를 막는다고 볼 수 없다. **부분 삭제를 발견하면 게임 시작과 백업 교체를 먼저 보류하고, 남은 데이터와 기존 OS 백업을 보관한 뒤 복구하도록 설계한다.**

저장 항목은 `/persist/HvM.dat`, `/persist/HUDLayoutV1-web.json`, `HeavyMach.KeyboardBindingsV1`, `HeavyMach.AimModeV1`이다. 기본 상태에서는 HUD 파일이나 설정 키가 없을 수 있다. ‘키가 없음’을 전부 손상으로 판단하지 않고, 이전 정상 백업에 있었던 항목과 비교한다. 정상 초기화·새 진행을 예전 백업으로 되돌리지 않도록 차이가 애매하면 복구할 진행을 선택하게 한다.

현재 웹 `Export save`는 사용자가 파일을 내려받는 방식이다. `PREVIOUS`와 가져오기 중단 기록은 localStorage에 있어 사이트 데이터 전체 삭제 때 함께 사라진다. 이들은 외부 백업을 대신하지 않는다.

### 방법 비교와 제안

| 방식 | 삭제 뒤 복구 | 사용자 조작·비용 | 적용 판단 |
|---|---|---|---|
| Tauri OS 파일 백업 | 웹뷰 저장을 삭제해도 OS 파일이 남으면 복구 | 자동 백업, 서버 불필요 | 현재 방식을 보완한다. |
| 웹 백업 파일 내보내기·가져오기 | 파일을 브라우저 밖에 보관했다면 복구 | 사용자가 파일 보관·선택. 내보낸 시점까지 복구 | 서버 없이 제공할 공통 수단이다. 자동 보존 요구 전체를 충족하지는 않는다. |
| 사용자가 지정한 파일에 자동 갱신 | 외부 파일은 남지만 재접근 권한·파일 선택이 필요할 수 있음 | 지원 브라우저에서 권한 허용 필요 | Safari까지 공통으로 쓸 기본안으로 삼지 않는다. |
| 외부 서버 자동 백업 | 마지막 업로드 완료본을 복구 | 서버 운영·인증·기기 간 충돌 처리 필요 | 웹에서도 별도 내보내기 없이 보존하려면 이 방향을 검토한다. |

파일 선택 API는 지원 범위와 권한 수명이 브라우저마다 다르다. 브라우저 내부 OPFS 파일을 일반 파일 시스템의 백업으로 취급해서는 안 된다. [Chrome 파일 접근 문서](https://developer.chrome.com/docs/capabilities/web-apis/file-system-access).

**제안은 Tauri의 OS 백업 보완을 먼저 확정하고, 웹은 외부 파일 복구와 서버 자동 백업의 범위를 보고서 검토에서 정하는 것이다.** GitHub Pages는 정적 호스팅이므로 서버 저장을 선택하면 별도 API와 저장소를 붙여야 한다. 게임 페이지와 자원 배포 주소는 유지할 수 있다. [GitHub Pages 구조](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages).

서버 저장을 선택한다면 다음 조건으로 설계한다. 정상 저장 완료본만 관찰하고 내용이 바뀐 때 전송한다. 탄환·프레임 단위 저장을 추가하지 않는다. 서버 응답을 받은 버전만 백업 완료로 표시한다. 네트워크가 끊기면 게임은 로컬 저장으로 계속하고 재연결 때 업로드한다. 삭제로 새로 생긴 빈 진행이 서버의 정상본을 덮지 않게 한다. 버전 번호로 기기 간 동시 갱신을 감지하고 이전 정상본을 보관한다. 접근 토큰·서버 비밀은 공개 저장소에 넣지 않는다.

사이트 데이터 삭제 때 로그인 상태나 기기 토큰도 사라질 수 있다. 서버 사본을 다시 찾으려면 재로그인이나 사용자가 따로 보관한 복구 정보가 필요하다. 저장 위치만 서버로 바꿔 모든 삭제 조건에서 무조작 복구가 된다고 약속하지 않는다. 오프라인에서만 진행하다 업로드 전에 데이터를 지웠다면 그 진행은 서버에 없다. 모든 플랫폼의 진행을 코드 하나로 복원하는 7번 과제는 이보다 넓은 별도 과제로 유지한다.

### 구현과 4번 검사 계획

1. **복구 기준본 준비:** 검사용 진행에서 무기·순서, 미션·경험치·강화, HUD·키·자동조준을 기록한다. 사용자 실데이터 대신 별도 프로필·저장 사본을 쓴다.
2. **Tauri 보완:** 전체 삭제·부분 삭제·복구 중단을 구분한다. 정상 백업과 남아 있는 진행을 먼저 보관한다. 시작 전 복구와 백업 교체를 순서대로 처리하고, 복구 실패 때 정상본을 유지한다.
3. **웹 구현:** 선택한 외부 보관 방식으로 복구한다. 백업 시점·성공·실패를 표시하고, 내보내기 취소·업로드 실패를 완료로 처리하지 않는다. 서버를 채택한다면 기존 게임 코드 대신 `Distribution/Web/`의 관찰·복구 계층과 별도 서버 폴더를 사용한다.
4. **삭제 검사:** 캐시만, DB만, 설정만, 사이트/웹뷰 전체, 새 브라우저 프로필을 각각 시험한다. 파일·설정 대조와 실제 게임 메뉴·HUD·전투 진입을 함께 확인한다. 서버 방식은 인증 복구·오프라인 진행·재연결·충돌도 검사한다.
5. **4번 저장·종료 검사:** 종료 직전 백업 오류, 중복 실행, 복구 중 강제 종료, 손상 파일, 실제 용량 부족, 앱 업데이트, 새 프로필 가져오기, 장시간 오프라인 후 완전 종료·재실행을 확인한다. 기존에 통과한 검사는 변경 영향을 받는 범위만 다시 실행한다.
6. **배포 판단:** 선택한 보존 방식과 검사 결과를 보고한다. 저장 손실·정상 종료 불가가 남으면 수정한다. 이후 최신 원격 main의 사용자 문서와 기여자 커밋을 확인하고 develop→main 순서로 병합·태그·릴리스한다.

**6번 연구 완료와 저장 보존 기능 완료는 각각 기록한다.** 외부 파일 방식으로 먼저 배포한다면 ‘미리 내보낸 파일로 복구’까지 제공한 것이다. 사용자가 요구한 자동 보존 전체를 완료로 표시하지 않는다. 이번 보고서 검토 전에는 새 서버 구축·게임 변경·main 병합을 진행하지 않는다.

### 후속 패치와 수동 조준점

2번의 PWA 재실행 권한·음향 조사와 3번의 장시간 성능 비교는 후속 과제로 둔다. 현재 사용자 플레이와 짧은 실행 검사는 통과했다. 추가 조사에서 플레이 중단·진행 손실이 발견되면 배포 전에 처리한다. Windows 설치본은 이후 단계로 남기고, Mac·웹 배포 완료와 구분한다.

사용자는 키보드·트랙패드가 있는 iPad에서 수동 조준점 표시를 숨기도록 요청했다. 표시는 HTML 요소가 아니라 `Sources/Web/WebGameView.cpp`의 `drawKeyboardIndicators()`에서 그린 8×8 테두리다. CSS로 숨길 수 있는 요소가 아니다. 해당 함수의 수동 조준 분기만 제거하고 메뉴 포커스·조준 좌표·발사 입력·자동조준 표시는 유지하는 좁은 변경을 계획한다. 기존 웹 코드 보존 조건에 대한 이번 사용자 요청의 변경 범위를 정확히 기록하고, 렌더러 전체 끄기나 생성된 Wasm 패치는 하지 않는다. 아직 표시를 숨기는 코드는 수정하지 않았다.

## 자동조준 사용 후 Mac 앱 종료 실패 수정

자동조준을 켠 뒤 Command-Q나 macOS 종료 메뉴로 앱이 종료되지 않았다. 원인은 Codex가 추가한 Tauri 백업 검사였다. 원래 게임의 조준 값은 off=0·manual=1·automatic=2인데 백업 검사는 0과 1만 허용했다. 게임 저장은 끝났지만 자동조준 값 2를 거부하면서 종료가 중단됐다. PR 기여자의 게임 구현과 공용 코어는 정상 값을 저장하고 있었다.

Tauri 백업 검사와 같은 오류가 있던 웹 실행기의 저장 내보내기 검사를 수정했다. 백업 실패를 알리는 창도 macOS 대화상자로 바꿨다. 기존 검사에는 자동조준을 켠 뒤 종료하는 조건이 빠져 있었다.

수정 전 Rust와 웹 검사에서 각각 `Invalid aim mode`, `Invalid aim setting` 실패를 재현했다. 수정 후 Rust 12개·JavaScript 18개가 통과했다. 웹에서는 실제 게임 버튼으로 자동조준을 켜고 내보내기·가져오기·오프라인 재실행 뒤 값 2가 복원되는 것을 확인했다. 최종 Mac 앱에서는 Command-Q와 종료 메뉴를 각각 실행한 뒤 프로세스 종료를 확인했다. 기존 슬롯이 열렸고, 새 백업에는 게임 진행 파일 3,624바이트와 자동조준 값 2가 기록됐다. [검사 기록](../evidence/tauri-quit-fix-20261101.json).


## 설치 우선 시작 화면과 저장 복구

첫 화면에서 **Install game**을 가장 크게 표시한다. **Play in browser**로 설치 없이도 플레이할 수 있다. 처음 페이지를 열 때는 메뉴만 내려받는다. 설치한 PWA를 처음 실행하거나 브라우저 플레이를 선택하면 게임 에셋과 WebAssembly를 받는다. 받은 용량·전체 용량과 검증률을 표시한다. 검사가 끝난 파일은 재시도 때 다시 받지 않는다.

Safari에서는 설치 버튼으로 공유 → 홈 화면에 추가 → 웹 앱으로 열기 순서를 안내한다. 설치 요청 API가 있는 브라우저에서는 설치 창을 연다. 설치형 앱에서는 설치 버튼을 숨기고 Play를 주 버튼으로 표시한다. 캐시를 지우거나 새 버전으로 업데이트하면 다시 다운로드한다.

![설치를 먼저 안내하는 웹 시작 화면](../assets/mac-web-pwa-20261101/launcher-install-first.png)

원작 `Main_BG`, `Main_Title`, `Common_Btn_OK`를 시작 화면에 재사용했다. 버튼 테두리는 원본에서 가져와 늘어나도록 나눴고 새 글자는 HTML로 표시한다. `Distribution/Web/launcher/`를 웹과 Tauri의 빌드 도구가 함께 사용한다. 게임 안의 메뉴와 자원 원본은 바꾸지 않았다.

Tauri에는 Export save·Import save·Restore last backup을 추가했다. macOS 파일 선택 창에서 백업을 내보내고 가져온다. 복구할 때 기존 진행과 백업을 `recovery/`에 보관한다. 복구 도중 앱이 종료되면 다음 시작에서 같은 파일로 복구를 이어간다. 게임 화면에서는 가져오기 명령을 사용할 수 없다.

확인한 결과:

- 설치 전 첫 방문에서 게임 파일 요청 0건. 설치 버튼 우선 노출과 iPad 설치 안내, 390×844·844×390·1024×768·1200×800 배치 검사 통과.
- 다운로드 실패 후 재시도, 검증된 파일 재사용, 실제 용량 표시, 재접속 때 게임 재다운로드 없음, 오프라인 시작까지 9단계 통과.
- Chrome 설치형 PWA에서 첫 실행 다운로드, 이동·점프·사격·정지, 저장 내보내기·가져오기, 오프라인 재실행과 저장 바이트 복원 통과.
- Tauri 저장 관련 Rust 11개·JavaScript 15개 검사 통과. 손상 파일 보존, 복구 중단, 저장소 용량 오류를 포함한다.
- 운영체제 저장 오류 검사도 통과했다. 쓰기 권한 거부와 16 MiB 임시 디스크의 공간 부족에서 이전 백업이 남았다. 공간을 비운 뒤 쓰기도 성공했다. 실제 백업 코드를 실행하는 별도 프로세스를 강제 종료해도 완성된 백업을 읽었고 다음 저장이 성공했다.
- 최종 Release 앱을 메뉴에서 강제 종료한 뒤 다시 실행했다. 시작 화면과 게임이 열렸으며 기존 백업의 해시는 같았다.
- 실제 Tauri Mac 앱에서 파일 내보내기·가져오기·복구 완료. 복구 전 진행과 기존 백업 2개를 보존했고, 복구 후 데이터는 내보낸 파일과 일치했다. 복구 후 게임 실행도 확인했다.

## iPhone·iPad·갤럭시 사용자 플레이와 권한 조사

사용자는 iPad Safari에서 키보드 이동·Space 점프·트랙패드 사격, 비행기 모드 전환과 오프라인 프로필 재진입을 확인했다. iPad Air 설치형 PWA에서는 틸트와 자동조준 사격을 확인했다. iPhone 설치형 PWA는 미션 1-4까지 정상 플레이하고 클리어했다.

2026-11-01 사용자 실제 플레이 확인: 갤럭시 순수 웹판에서 틸트 조작과 자동조준·수동조준이 모두 정상 동작했다.

동작 허용 팝업은 iPad Air PWA를 껐다 켤 때마다 나타난다는 제보다. 원본 `Web/shell.html`은 새 페이지에서 동작 권한 상태를 초기화하고 첫 입력 때 요청한다. ## 실행 구조와 저장

| 항목 | 기존 Mac | Tauri Mac | 브라우저·PWA |
|---|---|---|---|
| 게임 계산 | 네이티브 C++ 공용 코어 | 같은 코어의 WebAssembly 빌드 | Tauri와 같은 웹 빌드 |
| 화면 | AppKit·OpenGL | WKWebView·WebGL2 | 브라우저·WebGL2 |
| 소리 | OpenAL Soft | 웹판의 Web Audio 경로 | 웹판의 Web Audio 경로 |
| 진행 저장 | 기존 네이티브 파일 | IndexedDB와 별도 OS 파일 백업 | IndexedDB. 실행 화면에서 파일 내보내기·가져오기 |
| 실행에 필요한 파일 | 앱에 포함 | 앱에 포함 | 최초 다운로드 뒤 오프라인 캐시에 포함 |
| 업데이트 | 앱 교체 | 앱 교체 | 새 파일을 모두 검증한 뒤 기존 창이 닫히면 적용 |

세 실행부는 탄도·공격력·적 이동·스폰·자동조준의 같은 코어를 사용한다. 네이티브와 웹의 메뉴·입력·렌더링 연결부는 다르다. 실제 슬롯 메뉴에서도 삭제 버튼은 네이티브가 오른쪽, 웹이 왼쪽이었다. 해당 기존 구현은 변경하지 않았다.

Tauri·브라우저·네이티브 앱은 서로 다른 저장소를 쓴다. Tauri의 OS 백업은 웹뷰 저장소를 지운 뒤에도 복구에 사용할 수 있다. 브라우저에서는 사이트 데이터를 지우기 전에 Export save로 파일을 남긴다. 설치된 PWA와 브라우저의 저장 공유는 해당 브라우저의 프로필 정책을 따른다.

## 프레임 측정

Mac mini의 Apple M4 Pro에서 측정했다. 게임 앱과 성능 검사 브라우저를 순서대로 실행했다. 네이티브는 기존 XCTest가 실제 게임 타이머와 화면 출력을 사용하며, Tauri·Chrome은 화면 갱신 콜백과 게임 시각 증가량을 읽었다.

| 실행 | 장면·화면 크기 | 평균 갱신 간격 | 95백분위 / 최대 | 게임 갱신 |
|---|---|---:|---:|---:|
| 네이티브 Mac | 첫 미션 사격, 1200×800 | 16.665 ms | 16.911 / 18.442 ms | 약 60회/초 |
| 네이티브 Mac | 첫 미션 사격, 1920×1080 | 16.667 ms | 17.222 / 19.131 ms | 약 60회/초 |
| Tauri Mac | 첫 미션 연속 사격, 1200×768 | 16.668 ms | 18 / 18 ms | 60.01회/초 |
| Chrome 웹 | 첫 미션 시작 위치, 1200×800 | 16.667 ms | 17.6 / 17.8 ms | 60.04회/초 |
| Chrome 설치형 PWA | 첫 미션 연속 사격, 1200×800 | 16.669 ms | 18.3 / 18.8 ms | 59.98회/초 |

네이티브는 장면마다 준비 30회 뒤 180회를, Tauri와 Chrome은 각각 15초를 측정했다. 네이티브의 두 해상도·세 장면 검사에서 저장 함수 호출은 모두 0회였다. 프레임 처리 비용의 95백분위도 16.67 ms 안에 들어왔다. 장면 종료 뒤 화면·미디어·렌더러·오디오 객체의 해제를 확인했다.

Tauri의 첫 타이틀 측정에는 최대 101 ms, 슬롯 메뉴에는 최대 46 ms 간격이 각각 있었다. 최종 빌드의 재측정에서는 타이틀 평균 16.724 ms·95백분위 18 ms·최대 43 ms, 슬롯 메뉴 평균 16.742 ms·95백분위 18 ms·최대 65 ms였다. 메뉴에서 간헐적으로 긴 간격이 발생하는 현상은 남아 있다. 첫 미션 사격 구간에서는 최대 18 ms였다. Chrome GPU 검사에는 `ANGLE Metal Renderer: Apple M4 Pro`가 기록됐다.

이 표는 짧은 실행 결과다. 장면의 적 수·입력 시간·창 높이가 완전히 같지는 않다. 전체 프로세스 메모리·30분 플레이·음향 청취 비교는 남아 있다.

- 네이티브 실제 창: 슬롯 선택, 첫 미션, 이동·점프·사격·일시정지.
- 네이티브 기존 검사: 키보드 이동·조준·점프·사격, 모든 무기 선택과 발사, 두 화면 크기의 세 장면 프레임 검사.
- Tauri 실제 창: 기존 슬롯 재사용, 첫 미션, 연속 사격, 이동·점프·일시정지, 정상 종료. 이전 검사에서는 웹뷰 저장소를 별도 보관한 뒤 OS 백업으로 같은 슬롯을 복구했다.
- 공개 웹 주소: 첫 미션, 이동·점프·사격·일시정지, 동시 창 차단, 저장 내보내기·가져오기, 손상 파일 거부, 오프라인 재실행과 진행 복구.
- 설치형 PWA: Chrome 검사 인터페이스로 설치하고 독립 창을 열었다. 이동·점프·사격·정지와 저장 파일 검사를 통과했다. 네트워크를 끄고 재실행한 뒤 저장 3,624바이트 전체가 같음을 확인했고, 첫 미션에서 탱크 이동과 게임 시각 진행을 확인했다.

웹 자동 회귀는 별도 Chrome 프로필에서 실행했다. 기능 검사에 쓴 SwiftShader와 위 표의 실제 M4 Pro GPU 측정은 결과 파일을 나눴다.

## 웹·PWA 실행기에 추가한 것

`Distribution/Web/pwa/`에는 시작 화면·manifest·아이콘·Service Worker·저장 파일 관리만 둔다. 기존 게임은 `game/<내용 해시>/` 아래에 복사한다. 설치 또는 브라우저 플레이를 선택한 뒤 약 75 MB를 내려받고, SHA-256이 일치하면 게임을 연다.

웹 저장은 원래 저장 시점을 유지한다. 새 실행기는 시작 전 가져오기와 내보내기만 처리한다. 가져오기 전에는 기존 데이터 사본을 보관한다. 가져오기 중 브라우저가 종료되면 다음 시작에서 나머지 처리를 마친 뒤 게임을 연다. 동시에 열린 브라우저·PWA가 같은 저장소에 쓰지 않도록 Web Lock을 사용한다.

업데이트 검사는 잘못된 해시를 가진 배포를 주입해 확인했다. 잘못된 버전은 활성화되지 않았고, 이전 버전은 오프라인에서도 열렸다. 정상 업데이트도 열린 창을 즉시 교체하지 않았다. 창을 닫고 다시 열면 새 버전이 적용됐고 설정은 남아 있었다.

설치 검사에서 manifest의 상대 `id`가 계정 최상위 주소로 해석되는 문제를 발견했다. `id`를 생략해 고정된 `start_url`인 `/HeavyMach/`를 식별자로 사용하도록 수정했다.
