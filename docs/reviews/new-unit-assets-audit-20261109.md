# HeavyMach1 신규 유닛 전수 감사 — 2026-11-09

**새 유닛 8종은 모두 C++에서 정의를 추가한다. 원작 MCH/MAP로 새 유닛을 패키징한 방식은 아니다. 공중 6종의 동체는 별도 그리기 경로를 쓴다. 지상 2종은 기존 파츠 조립을 실제로 사용한다. 이동·조준·발사·피격·파괴의 복원 함수 재사용은 확인된다.**

따라서 정확한 설명은 “기존 복원 엔진에 새 C++ 등록·표시·행동을 추가하고 공통 기능을 재사용했다”이다. 원작 패키징·로직 전체를 그대로 사용했다고 설명하면 실제 구현을 과장한다. 다만 조사한 보고 문장 중 “원작 패키징과 동일하다” 또는 “새 C++ 구현이 없다”는 직접 주장은 확인하지 못했다. 확인하지 못한 주장까지 허위 보고로 단정하지 않는다.

**과거 보고 오류는 확인했다.** 탈락한 해리어 시안을 채택본으로 제시한 보고와, 제한된 장면만 보고 쉴카 포탑 틈을 해결했다고 판단한 보고가 있었다. 전자는 당시 정정됐다. 현재는 구형 GAA 설명과 최신 구현의 혼재, 미사용 PNG의 배포 포함, 플랫폼별 축소 결과 차이와 검증 범위 문제가 남아 있다.

## 1. 조사 대상과 기준

- 대상: Yak-141, Harrier, F-35B, Lux F-22, Lux Su-57, Lux MiG-31, 쉴카, 퉁구스카 전부.
- 소스: `de492285c028fa741324fe5328f138b96bdd509d`. 감사 시작 시 main `191728e310158a55df1164ee452b19b48fa97e57`과 제품 트리가 같았다.
- 원작: 로컬 HeavyMach 1.13 IPA, SHA-256 `477c672f92110c6020be3f744dfa7a3456739e6f970c66715e3b7b3cd32b7776`. 원본 파일과 사용자 저장을 변경하지 않았다.
- 방법: 실제 파일 magic·PNG chunks·해시·알파 분포, 생성 출력과 manifest, C++ 호출 경로와 원작 분석 산출물, 생성 당시 사용자 지시와 보고, 기존 테스트의 검사 내용, 플랫폼 패키지 내부 파일을 대조했다. 현재 소스로 데이터 인벤토리를 컴파일·실행했다.
- 원작 저자의 소스가 확보된 상태는 아니다. 현재 C++은 원작 Objective-C ARM 실행물을 근거로 복원한 구현이다. 디컴파일 자료를 원작 소스라고 부르지 않는다.
- 이번 작업은 감사다. 게임 코드·PNG·배치·저장·설치 상태를 바꾸거나 새 게임을 배포하지 않았다. 문서와 검사 증거를 기록했다.

## 3. 확장자·인코딩·크기·생성 이력

원작 이미지 695개와 RawData 46개는 원작 IPA의 대응 파일과 모두 바이트가 같다. 원작 이미지의 실제 포맷은 CgBI PNG 679개와 JPEG 16개다. `Icon.png`가 JPEG인 예외도 원작 IPA와 동일하다. 이를 새 유닛의 확장자 위장으로 판단하면 안 된다.

신규 유닛 PNG 22개는 모두 실제 표준 PNG RGBA8이다. 다른 포맷에 `.png`만 붙인 사례는 발견하지 않았다. 현재 사용하는 원본 파일은 항공기 6개와 GAA 시트 5개, 합계 11개다. 대형 원본을 `Art/Extensions`에 보관하고 처음 읽을 때 crop·축소한다. 원작의 작은 개별 그림 및 타일 방식과 기술적으로 다르다.

표의 항공기 정수 크기는 축소 캐시의 픽셀 수다. 실제 논리 표시 높이는 `width × aspect`이며 정수로 반올림하기 전 값이다. 예를 들어 Yak는 약 37.333, F-22는 약 48.698이다.

신규 22개 총 저장 크기는 31,953,336바이트다. 활성 11개는 15,873,012바이트다. 원작 이미지 695개 합계는 28,230,434바이트다. 신규 파일 용량이 크다는 사실과 게임에서 동시에 사용하는 메모리 크기는 다르다.

신규 PNG 22개 모두 로컬 imagegen 출력과 SHA-256이 같다. 채택 후 스크립트로 PNG를 다시 그리거나 재인코딩했다는 증거는 없다. 그림 선택·crop·축소·조립은 별도의 런타임 코드에서 실행한다.

생성 manifest의 SHA 기록 83건을 대조했다. 현재 자료 73건, 이전 버전 before 해시 4건, 로컬 build에서 찾은 참고 그림 6건으로 모두 설명된다. 마지막 6개는 Git 미추적 자료라 새 clone만으로 참고 파일까지 복원할 수 없다. 생성 모델을 다시 호출해 같은 픽셀을 얻는 결정론적 재생성은 증명하지 않는다.

GAA 최종 제작에는 원작 그림뿐 아니라 먼저 만든 Harrier/F-22 및 기존 생성 시안·레이더를 참고했다. “원작 그림만 직접 참고했다”는 설명은 맞지 않는다. 실제 생성 완료 이벤트 16건(VTOL v3 3건·Lux gold 3건·GAA runtime-style 3건·integrated 6건·쉴카 포탑 1건)의 프롬프트는 저장본과 모두 문자 단위로 같았다. 입력 경로·SHA를 manifest와 대조했고 추가 불일치를 발견하지 못했다. runtime-style은 실제 Harrier v3를 입력했다. 쉴카 포탑은 경로가 달라도 입력 두 파일의 SHA가 같았다. 일부 중간 입력과 원작 헬기 참조의 해시는 최종 manifest에 없고 생성 이벤트에 남아 있다. 프롬프트의 형상·회전 요구를 그림이 충족했는지는 이 검사로 판정하지 않는다.

알파에도 차이가 있다. 활성 신규 11개의 비영 알파 최빈값은 253이고, 비교한 원작 헬기 2개·탱크 1개는 255다. 신규 항공기 비영 픽셀의 약 93.3~95.3%는 알파 250 이상이다. 이 수치만으로 눈에 띄는 반투명 결함을 단정하지 않는다. 전체 분포는 증거에 보존했다.

`tools/generate_ground_aa_art_table.py`를 임시 트리에서 실행했다. 현재 `GroundAAArt.inc`의 57행과 바이트가 같았다. 최종 manifest 하나에 일반 부품 9행·레이더 48행이 들어 있다. `previous_manifest`는 이력 연결이며 실행 중 여러 manifest를 병합하는 기능은 아니다.

## 4. 원작 경로와 새 C++ 경로

원작 데이터는 `GameData::loadDirectory`에서 MCH/MAP를 파싱하고 `spawnEnemy → makeMachFromDefinition → enemyParts → attachParts`로 이어진다. 신규 유닛은 `addVTOLExpansion`, `addFighterExpansion`, `addGroundAAExpansion`이 이미 읽은 구조체를 직접 추가·수정한다. 원본 MCH/MAP는 그대로 두고 메모리에서 확장한다.

| 데이터 단계 | 무기 | 파츠 | 기체 정의 | 맵 | MAP 적 배치 |
|---|---:|---:|---:|---:|---:|
| 원작 판독 직후 | 160 | 294 | 720 | 43 | 1,182 |
| VTOL 추가 | 160 | 297 | 723 | 43 | 1,334 |
| Lux 추가 | 163 | 303 | 726 | 43 | 1,334 |
| GAA 추가 | 184 | 366 | 740 | 43 | 1,486 |

8종이 런타임 기체 정의 20개로 늘어난다. 공중 6종은 각 1개, 지상 2종은 각 미션별 7개다. 추가 파츠 72개·무기 24개다. 현재 소스를 직접 컴파일한 읽기 전용 인벤토리로 확인했다.

VTOL 152개와 GAA 152개는 메모리의 `MapDefinition.enemies` 뒤에 추가한다. Lux 72개는 MAP 목록에 없으며 별도 14개 증원 조건에서 생성한다.

공중 6종의 파츠 트리는 보이지 않는 Anchor와 무기만 가진다. 동체는 `GameSession.cpp:467–480`의 `graph.vtol` 분기에서 별도 `DrawSprite`로 만든다. 원작 헬기의 공통 이동 계산을 수행한 뒤 새 pitch로 최종 회전을 덮는다. 분사 효과는 원작 그림을 쓰지만 위치·진동·회전·알파 계산은 새 구현이다.

지상 2종은 Body→Turret→Radar/Gun/Missile 트리를 만들고 기존 재귀 소켓 조립과 `drawParts/drawWeapon`을 실제로 실행한다. 이후 `configureGroundAADraw`가 타일 이름·분할 수·프레임·레이더 위치를 바꾼다. 크기는 `GameSession`의 `addPart/groundAAPartSize` 및 플랫폼 crop·축소 코드가 처리한다. 레이더는 원작 자동 애니메이션 유형 대신 2초에 24프레임을 계산한다. 피격 범위는 고정 사각형으로 덮는다.

공통 전투 경로 `Enemy::tick → GobHvMach::tick → processLand/processFly`, `processWeaponAI → tickWeapon → spawnBullet → tickBullet → onDamage/onDestroy`는 실제로 공유한다. 단, Lux의 AI 시간·묶음 발사 필드는 새로 추가했다. 공통 파일을 호출한다는 사실이 그 파일 자체에 변경이 없다는 뜻은 아니다.

원작 `processFly`, `processAI`, 재귀 소켓, 몸체 프레임 및 `makeMachFromName`의 보존된 분석 산출물과 해당 복원 함수를 대조했다. 전체 원작과 확장판의 동작 동일성을 인증하는 범위는 아니다. 특히 GAA는 공통 난수열을 소비하므로 원작 적의 시점별 랜덤 결과까지 유지된다고 주장할 수 없다.

| “기존 미사일의 발당 피해·그림·비행·충돌을 재사용한다.” | Lux의 공통 처리 재사용은 사실. 탄속·발사 수·간격 등은 바뀌며 앞선 수치 표에도 명시돼 있다. |
| “원작의 지상 이동·지형 충돌·무기 조준·피격·폭발 코드를 연결했다.” | 복원 함수 호출 경로가 있다. 원작 저자 소스 그대로 사용했다는 의미로 쓰면 안 된다. |
| “기존 지상 유닛의 부품 조립과 움직임을 재사용” | 실제 소켓 조립을 사용한다. C++ 등록과 별도 표시 분기를 보충해야 한다. |
| “원작과 같은 파츠 흔들림 적용” | 범위가 넓다. 계산 공유와 옵션·진폭 동일성을 구분해 정정할 필요가 있다. |

사용자는 VTOL에 “무기는 다른 헬기 유닛들이 쓰는 무기 재사용”과 “기체 기울기 자체 구현”을 지시했다. GAA에는 새 외형·파츠를 허용하면서 기존 파츠 조립과 동작을 확인하라고 했다. 독립 레이더 회전·무장·스폰 변경도 지시했다. 새 코드의 존재 자체를 무단 구현으로 볼 수는 없다. 그러나 이 지시를 특정 C++ 등록·원작 데이터 포맷 우회 방식까지 명시 승인한 증거로 확대하지 않는다.

쉴카 포탑 비율 변경과 현재 흔들림 유지에는 후속 사용자 허용이 있었다. Lux의 빠른 진입은 구현자의 선택이었으며 사용자가 결과를 본 뒤 허용했다. 최초 구현 시 재량과 사후 허용을 구분한다.

당시 적용된 아트 스킬은 실제 기체 기준·원작 색조/질감·채택본 보존·게임 크기 비교를 요구했다. 새 유닛을 반드시 원작 MCH로 패키징하라는 직접 문구는 확인하지 못했다. 후대 스킬을 당시 위반의 유일한 근거로 소급 적용하지 않는다. 문서에 구현 방식을 공개한 사실도 사용자의 특정 방식 승인을 대신하지 않는다.

과거 해리어 오류는 [당시 보고와 정정](../public/ground-aa-art-20261028.md)에 남아 있다. v1 `aaa54c606b50`, 생성 입력 v2 `b40e1e5b9cae`, 앱 v3 `9a523efede9a`는 서로 다른 파일이다. 원래 보고 커밋 `70d3454b`와 정정 `88bb44ce`를 대조했다. 개인 대화 전문은 공개 근거에 넣지 않았다.

조사 범위는 해당 8종의 생성·구현 당시 관련 세션, 현행 설계·공개 문서, 관련 커밋이다. 모든 외부 사이트의 과거 버전과 모든 세션을 확인했다는 의미는 아니다. 의도적인 기만 여부는 이 증거로 판정하지 않는다.

## 6. 플랫폼 패키지와 축소 계산 확인

iOS 일반 앱 빌드 산출물, 설치된 네이티브 Mac 앱, 11월 7일 일반 Android APK, 당시 배포용 웹 산출물에서 신규 PNG 22개·RawData 46개가 저장소와 모두 같았다. 웹은 JS의 패키지 파일 오프셋으로 `.data`에서 추출해 확인했다. 이번에 휴대폰 내부 앱을 다시 추출하거나 공개 웹을 새로 내려받은 것은 아니다.

설치된 Tauri 실행 파일에서는 웹 자원 4개에 대응하는 Brotli 압축 바이트 전체를 찾았다. 각 데이터를 해제한 해시가 검사한 웹 패키지와 같았다. 실행 파일 SHA는 `acd71dbc6a53947bd754f3cef3d6d1ffa662b10f83e3de6450d2253a7e708578`이다.

Apple의 `HMMedia.mm`은 CoreGraphics의 High 보간을 사용한다. `WebMedia.cpp` 및 Android `Media.cpp`는 면적 평균 축소를 구현한다. 같은 crop·입력·목표 크기로 Mac에서 두 계산을 직접 실행했다.

## 7. 기존 검사가 보장하지 않는 것

기존 테스트 소스와 유효한 이전 결과를 참고했다. 이번에 일반 게임 테스트 전체를 다시 실행했다고 보고하지 않는다.

- VTOL/Fighter 전투 테스트의 일부는 탄을 표적의 hitbox 안에서 시작한다. 피해 처리 연결은 확인하지만, 플레이어가 거리·각도를 맞춰 쏜 탄의 실전 명중이나 그림과 hitbox 정합성을 확인하지 않는다.
- GAA 조립 테스트는 크기·소켓·사각형의 겹침을 본다. 실제 PNG 불투명 픽셀이 반동·경사에서 이어지는지 읽지 않는다.
- GAA 지형 테스트는 152개 배치의 착지·이동을 검사한다. 모든 지형·거리·조준 방향 조합을 플레이한 결과는 아니다.
- 파일 존재 및 draw 명령 검사는 원작 포맷·인코딩·원작 조립 동일성 검사가 아니다.
- 이번 직접 실행: 원작/신규 파일 해시와 포맷 조사, 생성 표 재생성, 현재 Core 소스 인벤토리 컴파일·실행, 배포 산출물 추출 비교, 축소 함수 비교. 새 실기기 전투·게임 전체 회귀는 실행하지 않았다.
