# 신규 유닛 구조 핫픽스 계획 — 2026-11-09

**현재 보이는 8종의 외형·크기·부품 위치·움직임·사격을 보존하면서, 제작 결과를 정식 게임 데이터로 내보내고 기존 유닛과 같은 로더·파츠 조립·전투 경로로 실행하도록 바꾼다.** 원작에 없는 추가 동작은 공통 데이터 계약과 공통 처리로 명시한다. 유닛 이름으로 실행 경로를 고르는 전용 코드를 남긴 채 파일 이름만 바꾸는 방식은 이 계획의 완료 상태가 아니다.

현재 단계는 계획 수립이다. 게임 코드·에셋·설치본·운영 게임을 변경하지 않았다. [감사 결과](new-unit-assets-audit-20261109.md), [경위서](new-unit-implementation-incident-20261109.md)에 현재 구현과 보고 문제를 연결했다.

현재 해시로 고정한 소스·자원은 878개다. [입력 목록](../evidence/new-unit-hotfix-20261109/preserved-inputs.json)에 보존했다. 장면별 GPU 캡처와 전투 추적은 아직 수집 전이며, 구현의 첫 단계에서 기준판을 직접 실행해 확보한다.

## 3. 원작 데이터로 옮길 범위와 추가 계약

원작 레코드 구조를 그대로 따를 범위는 무기 기본 수치, 파츠 타입·타일 수·소켓, 기체 HP/EXP/type·재귀 파츠 트리, 맵 적의 이름·좌표와 원작 이름 규칙으로 판정되는 보스 여부다. MAP type11에는 이름24바이트와 좌표8바이트가 있으며 독립 보스 bool 필드는 없다. 새 `.mch`라는 확장자 아래 다른 구조를 넣지 않는다. 기존 파서를 수정하지 않고 읽는 왕복 검사를 먼저 만든다. 24바이트 이름 필드의 종료 문자, 레코드 크기·타입·자식 수·순서·중복 ID·누락 참조를 검사한다.

원작 파일은 읽기 입력으로 고정한다. 제작 도구는 원작 레코드와 새 레코드를 포함하는 **별도 실행용 패키지**를 내보낸다. 앱은 선택된 패키지의 `WeaponInfo.mch/PartsInfo.mch/MachInfo.mch/*.map`을 같은 `loadDirectory` 경로로 읽는다. 기존 레코드와 원작 데이터 값이 같은지 별도 비교하고, 패키지 내부 변경 목록을 기록한다. 실행 중 C++ factory가 누락 정의를 다시 만들어주는 우회 동작은 제거한다. 실행용 MCH/MAP에는 새 레코드가 들어가므로 배포본 전체 해시는 원작과 달라진다. 원본 보관 파일의 바이트, 실행용 패키지 안의 기존 레코드·순서·알 수 없는 원본 필드 보존을 각각 검사한다. 기존 레코드를 선택 필드만으로 다시 쓰다가 정보를 누락하지 않도록 원본 노드/페이로드 복사와 새 노드 추가를 기본으로 삼는다.

다음 값은 현재 원작 레코드로 표현할 수 없다.

|---|---|---|

현재 묶음 발사는 이미 Combat의 burstGroupSize 필드로 실행한다. 이 항목은 이름 분기 제거가 아니라 C++ 설정값을 명시적 데이터로 직렬화하는 수정이다.

추가 계약은 버전·허용 필드·기본값·검증기를 갖는 별도 데이터로 설계한다. 원작 MCH 레코드 뒤에 임의 바이트를 붙여 같은 형식인 것처럼 처리하지 않는다. 정확한 파일명과 스키마는 첫 구현 커밋에서 원작 필드 대응표·호출부·검사와 함께 확정한다. 데이터로 값을 옮긴 것만으로 완료하지 않고, 기종 이름을 검사하는 전용 등록·그리기·crop 경로가 제거됐는지 확인한다.

## 4. 그림과 패키징 전환

새 그림을 다시 생성하지 않는다. 채택된 생성 출력은 저작 원본으로 보존하고, 내보내기 도구가 기록된 crop·크기·보간·알파 처리를 실행해 게임 크기의 파생 파일을 만든다. 원본 SHA, 처리 도구/환경, 입력 프롬프트·참조의 계보, 출력 SHA와 소비 파츠 ID를 한 목록으로 연결한다. 구형 GAA 11개는 이력에 남기고 실제 게임 패키지의 자원 목록에서는 제외한다.

플랫폼별 현재 축소 결과를 보존하기 위해 내보내기 설정에 Apple 및 Android 및 웹 각각의 기존 처리 조건을 명시한다. Android와 웹은 같은 면적 평균 계열이지만 합산·분모 계산이 달라 각 실제 출력이 일치할 때만 같은 프로필로 묶는다. 플랫폼은 빌드할 때 해당 파생 자원을 선택한다. 게임 실행 코드가 기체 이름을 보고 다른 이미지 알고리즘을 수행하지 않도록 한다.

파일 검사에는 확장자뿐 아니라 magic·PNG chunks·색/알파 형식·디코드 크기를 포함한다. 원작은 주로 CgBI PNG이고 현재 신규 원본은 표준 RGBA PNG다. **CgBI로 변환하기만 하면 같은 화면이 된다고 가정하지 않는다.** 현행 로더는 CgBI의 알파를 되돌렸다가 다시 곱하므로 낮은 알파의 채널 값이 바뀔 수 있다. 게임 크기 결과를 포장하고 공통 로더로 다시 읽은 최종 텍스처의 전 픽셀을 비교한 뒤 형식을 확정한다.

기본 목표는 기존 공통 PNG 로더가 지원하는 실제 PNG 계약 안에서, 신규 전용 디코더 없이 같은 출력 바이트를 얻는 것이다. 표준 PNG를 사용할 경우 CgBI와 다른 인코딩임을 자원 명세에 적는다. CgBI 동등성·알파 보존이 확인되지 않은 상태에서 원작 최적화까지 같다고 보고하지 않는다. 표준 PNG 기본안은 현행 premultiply 계산의 역변환 입력을 찾아 straight RGBA8로 기록하는 방식이다. float32 산술 검사에서 유효한 알파/채널 조합32,896개 모두 역변환 입력이 존재했다. 실제63개 이미지의 compiled loader·색 보정·POT 여백·GPU 업로드까지 일치하는지는 아직 실험 전이다. [산술 검사 소스](../evidence/new-unit-hotfix-20261109/premultiply-inverse-probe.py)와 [결과](../evidence/new-unit-hotfix-20261109/premultiply-inverse-probe.json)를 보존했다. 알파0의 RGB는0으로 만들고 채널이 알파보다 큰 비정상 입력은 거절한다. 형식 변환 실험이 실패하면 그 단계를 수정하고 다시 비교하며 시각 보존 기준을 낮추지 않는다.

레이더 48프레임의 중심점은 소수점이다. 그림을 정수 픽셀만큼 옮겨 고정 중심으로 합치면 위치가 바뀔 수 있다. 시트의 셀 경계·투명 여백·샘플링 이웃·프레임별 피벗을 함께 설계하고 공통 파츠 계약에서 처리한다. 한 장으로 합치는 경우 LINEAR 필터의 이웃 프레임 번짐까지 검사한다. 여러 파일 유지 여부는 이 비교 결과로 정하며, 어느 쪽이든 GAA 이름별 alias와 실행 중 crop은 제거한다.

## 6. 시각·전투·성능 검사

같은 플랫폼에서 같은 소스 환경·seed·입력·시간·카메라·배율·OS/GPU 조건을 맞춘다. 기준판을 두 번 실행해 자체 재현성을 먼저 확인한다. GPU의 비결정적 차이는 기준판 반복 결과로 식별하며, 후보 실패 뒤 허용 오차를 늘리지 않는다.

1. **텍스처:** 항공기6개·GAA57개 논리 이미지의 크기·알파·최종 업로드 바이트 대조. 같은 처리 환경의 텍스처는 바이트 일치를 목표로 한다.
2. **화면:** 항공기 정지·상승·하강·전후 이동·진입·사격·피격·파괴, GAA 차체2프레임·레이더24프레임·조준·반동·평지·경사·정지/재개. 소수점 위치와 레이어를 확인한다. drawParts의 프레임 갱신과 drawWeapon의 반동 감쇠를 두 번 실행하지 않도록 기준판·후보판을 별도 세션으로 비교한다. 스크린샷뿐 아니라 공통 파츠로 만들어진 draw의 기하·픽셀 영역을 비교한다.
3. **전투:** 플레이어20무기와 필살기3종을 실제 선택·사격·탄환 비행·충돌 경로로 검사한다. 표적 내부에 탄을 생성하는 기존 피해 단위 검사는 보조로 유지한다. 동체 윤곽과 피격 범위를 겹쳐 보고 발사점·명중 시점·피해·파괴를 비교한다. 현재 항공기의 weaponPos/muzzlePos 분담이 AI 거리·조준 계산에 영향을 주므로 탄 출발점뿐 아니라 AI 단계와 발사 tick도 비교한다.
4. **스테이지:** 35개 스테이지를 모두 로드하고 신규304개 정적 생성, 기존1,182개, Lux14회·72기 및 보스·맵 끝 트리거를 검사한다. Survival과 나머지 원작 맵도 로드·기존 상태 보존을 확인한다.
5. **원작 유닛:** 전체 원작 정의를 로드하고 참조 무결성을 검사한다. 같은 입력·난수로 원작 지상/공중/보스·플레이어의 전투·draw 추적을 비교해 공통 처리 변경의 영향을 잡는다.
6. **저장·성능:** 설치 전후 저장 해시, 정상 저장·복원 코드·재실행·백그라운드 복귀, 사격 중 저장 호출, decode 횟수·패키지 크기·텍스처 메모리·프레임 시간·음향을 같은 장면에서 비교한다. 새 런타임 crop·resize 호출은 없어야 한다.

현재 제공 중인 플랫폼 전체가 위 범위다. Tauri Windows는 저장소에서 후속 개발 상태이며 이번 핫픽스 완료 플랫폼으로 표시하지 않는다. Android의 현재 개발 서명 APK와 Apple의 개발 서명 설치를 스토어 배포·Developer ID 공증 완료로 바꾸어 쓰지 않는다.

iPhone/iPad 검증 앱은 앞선 작업에서 무료 개발 서명의 앱 수 제한으로 설치가 막혔다. 구현 시작 전에 실제 서명·설치 가능 상태를 확인한다. 기존 일반 앱과 다른 앱을 임의 삭제하지 않는다. 유효한 별도 검증 앱 또는 정식 후보의 수동 실기기 검사로 필요한 조건을 확보하며, 실제 기기 확인을 못한 상태는 해당 플랫폼의 배포 차단 사유로 남긴다.

모든 후보 검사를 끝낸 뒤 정식 반영한다. 각 플랫폼의 후보·빌드·서명·설치·실행·게시 결과를 따로 기록한다. 한 플랫폼의 성공으로 나머지를 완료 처리하지 않는다.

## 8. 브랜치·PR·릴리스 순서

이번 계획과 경위서는 develop에서 출발한 `audit/new-unit-assets-20261109` 작업 브랜치에 기록한다. 현재 문서 작성 요청으로 제품 main 병합이나 게임 배포를 실행하지 않는다.

핫픽스 구현을 시작할 때 다음 순서를 따른다.

1. `git fetch origin main develop` 후 양쪽 최신 SHA·사용자 직접 수정 문서를 기록한다. 필요한 감사/계획 문서는 작업 PR로 develop에 먼저 통합한다.
2. 최신 develop에서 `fix/new-unit-resource-contract`를 분기하고 전용 worktree를 만든다. 다른 checkout의 미커밋 작업·원본·빌드를 그대로 둔다.
3. 실제 최신 태그를 조회해 새 버전을 정하고 앱 빌드 번호·Android versionCode·Tauri 버전 및 웹 버전 생성 규칙을 작업 브랜치에서 확정한다. 단계별 구현·근거·검사를 커밋하고 **작업 브랜치 → develop PR**을 만든다. 독립 검토 지적과 실패를 고친 뒤 merge commit으로 병합한다.
4. 통합된 develop SHA로 후보를 빌드·검증한다. main/develop을 다시 fetch하고 공통 조상 이후 양쪽 문서와 병합 후보 본문을 대조한다. 최신 사용자 수정은 문단별로 보존한다.
5. **develop → main PR**을 만든다. `branch-flow` 등 실제 필수 검사를 확인하고 merge commit으로 병합한다. feature/fix에서 main 직접 병합, 훅 우회, force-push, 기존 태그 이동은 하지 않는다.
6. main 병합 SHA에 후보 검증을 거친 버전의 새 annotated tag를 붙인다. main에서 버전 파일을 직접 고치지 않는다. 릴리스 manifest에 해당 SHA·앱 버전·웹 콘텐츠 해시를 연결한다. 기존 릴리스 파일을 덮어쓰지 않는다.
7. main SHA로 정식 산출물을 빌드하고 후보와 게임 코드·자원·설정 차이를 검사한다. 플랫폼별 설치 및 공개 웹·다운로드 게시 후 실제 버전과 저장·전투를 확인한다.
8. 하위 저장소의 원격 커밋·릴리스를 확인한 뒤 필요하면 허브 포인터도 허브 작업 브랜치 → develop → main 절차로 갱신한다. 허브의 다른 변경을 섞지 않는다.

웹의 `gh-pages`는 main 제품 산출물을 게시하는 전용 배포 브랜치다. 이를 제품 소스의 병합 경로로 사용하지 않는다. 기존 `Distribution/Web/scripts/package.py`와 `publish.py`, 릴리스 도구를 사용하며 생성된 JS/Wasm에 임의 패치를 넣지 않는다.

기존 Android/Tauri 작업 당시의 보호 조건에서 변경이 필요한 파일은 아래 범위로 한정해 계획에 드러냈다. 이번 핫픽스 구현은 같은 소비 경로를 만들기 위해 공용 Core와 각 미디어 로더를 함께 고치는 작업이다. 기존 기여자의 코드·저장·GPU 복구 수정과 커밋 이력은 보존한다.

## 10. 중단 조건과 복귀 방법

필수 장면에서 외형·움직임·사격이 달라지거나 원작 유닛·저장 회귀가 나오면 해당 후보의 배포를 중단한다. 실패 자료와 기준판을 보존하고 원인을 고친다. 일부 플랫폼이 실패하면 전체 완료를 선언하지 않는다.

정식 반영 전에는 이전 앱·APK·Tauri ZIP·웹 버전 manifest와 해시를 보존한다. 설치 전 사용자 저장을 읽기 백업하고 일반 앱을 삭제하지 않는다. 호환 스키마를 유지해 이전판으로 돌아갈 때도 진행을 읽을 수 있게 한다.

배포 후 문제 발생 시 웹은 보존한 이전의 완전한 콘텐츠 묶음을 다시 게시하며 저장소를 비우지 않는다. Android는 다운그레이드 설치가 막힐 수 있으므로 이전 정상 코드를 새 versionCode로 다시 패키징하는 복귀 후보를 마련한다. Apple·Mac·Tauri도 같은 앱 식별자와 저장 경로를 유지한 복귀 빌드를 쓴다. 사용자 데이터 삭제를 복귀 절차로 삼지 않는다.

소스 복귀는 작업 브랜치의 revert 커밋 → develop → main으로 진행한다. main reset·force-push·태그 재지정 없이 새 복귀 릴리스로 기록한다.
