# 신규 유닛 구현·검증·보고 경위서 — 2026-11-09

작성 주체: 구현·검증·보고를 수행한 Codex. 조사 기준: main `191728e310158a55df1164ee452b19b48fa97e57`과 같은 제품 소스·자원. 시각은 한국 표준시다.

**새 유닛을 기존 게임에 추가하면서 원작의 데이터 제작·등록·에셋 소비 규칙을 충분히 대조하지 않고 별도 C++ 등록과 표시 처리를 넣었다. 일부 공통 함수를 재사용한 사실과 원작 구조를 따른 범위를 구분해 검증·보고하지 못했고, 그 구현이 공개 소스와 여러 플랫폼의 배포본에 포함됐다.**

이 업무는 구현을 맡은 Codex의 책임이다. 사용자가 파일 확장자·내부 인터페이스·패키징 규칙까지 하나씩 지정해야 할 일이 아니었다. 사용자에게서 새 유닛의 외형과 기능을 만들라는 지시를 받은 뒤, 기존 유닛과 연결되는 제작·실행 계약을 확인하고 차이가 필요한 지점을 설명했어야 했다.

현재 외형을 바꾸지 않고 구조를 바로잡는 [핫픽스 계획](new-unit-hotfix-plan-20261109.md)을 작성했다. 이번에 완료한 작업은 조사·계획·경위 기록이다. 공개 게임의 구조 수정과 새 배포는 아직 수행하지 않았다.

## 1. 요구와 실제 구현의 차이

사용자는 원작 게임의 색조·디자인에 맞는 새 항공기, 원작 무기 재사용, 기체 기울기, 럭스루나에의 무장·증원, 지상 유닛의 기존 조립·움직임과 독립 레이더를 요구했다. GAA 제작 때는 새 그림과 파츠를 허용하면서 기존 유닛의 조립 상태와 동작을 확인하라고 명시했다.

실제 구현에서는 다음 방식이 들어갔다.

| 영역 | 실제 상태 | 놓친 검증·설명 |
|---|---|---|
| 기체·파츠·무기 | `VTOL.cpp/Fighters.cpp/GroundAA.cpp`가 로딩 뒤 C++ 구조체를 만든다. VTOL 무기는 기존 정의 참조, Lux/GAA 무기는 복사·추가한다. | 새 정의를 원작 MCH로 작성하고 기존 판독 경로로 읽는 제작 과정과 달랐다. |
| 스테이지 | VTOL/GAA 배치를 실행 중 계산해 메모리 목록 뒤에 붙인다. Lux는 별도 증원 조건을 사용한다. | 원작 MAP 정적 배치와 새 증원 기능의 경계를 명확히 구분해야 했다. |
| 공중 동체 | 보이지 않는 Anchor와 무기 파츠를 만들고, 동체·배기는 별도 `DrawSprite`로 그린다. | 공통 이동/전투를 재사용했다는 설명이 동체 조립까지 같다는 보증처럼 읽힐 수 있었다. |
| 지상 부품 | 기존 소켓 조립·무기 처리는 사용한다. 이후 별도 가상 이미지·크기·레이더 분기가 표시를 바꾼다. | 조립 함수 공유와 전체 에셋·프레임 처리 동일성을 구분하지 못했다. |
| 이미지 | 대형 표준 PNG를 Extensions에서 읽고 플랫폼별로 crop·축소한다. | 원작 CgBI PNG·작은 부품/타일 소비 방식과 차이가 있다. 원작과 신규의 기술 계약을 함께 검사해야 했다. |
| 보고 | 재사용 기능과 빌드·플레이 검사 결과를 중심으로 설명했다. | 무엇이 원작 공통 경로이고 무엇이 신규·우회 구현인지 한 문맥에서 충분히 드러내지 못했다. |

일부 구현 문서에는 C++ 등록과 PNG 축소가 기록돼 있었다. 그 기록의 존재만으로 원작 구조와의 정합성 검토, 사용자에게 필요한 차이 설명, 플랫폼별 완료 검증을 대체할 수는 없다.

## 3. 확인된 보고 오류와 실제 재사용

첫째, 탈락한 해리어를 채택본이라고 제시한 보고는 사실과 달랐다. v1 `aaa54c606b50`, 생성 입력 v2 `b40e1e5b9cae`, 앱 v3 `9a523efede9a`의 해시가 서로 다르다. 보고 전에 참조·생성·앱의 파일 연결을 검사하지 않은 책임이 있다.

둘째, 쉴카 포탑 틈을 일부 장면만 확인하고 해결됐다고 판단했다. 이동·반동·경사 조건과 실제 불투명 픽셀의 접합까지 확인하지 못한 상태를 완료로 확대했다.

셋째, “원작과 같은 파츠 흔들림”은 계산 공유와 설정 동일성을 구분하지 않은 표현이다. 원작 적 생성에서는 꺼진 bounce 옵션을 새 GAA에는 켰다. 후속 사용자 유지 지시는 현재 효과를 보존할 근거지만, 최초부터 원작 적과 같은 설정이었다는 근거는 아니다.

넷째, 현행 GAA 설명에는 초기8방향·PNG11개와 최종24방향·활성 시트5개 설명이 섞여 있다. `docs/weapon-validation-procedure.md`에도 초기 레이더8방향 문구가 남아 있다. 현행 설명과 과거 검사 시점을 분리해 정정할 대상이다.

공통 이동·소켓 조립·조준·발사·피격·파괴 함수가 실제 호출되는 점도 확인했다. 따라서 재사용이 전혀 없었다고 쓰는 것은 사실과 다르다. 문제는 이 재사용 범위를 넘어 제작·등록·표시 방식까지 원작과 같다는 인상을 주고, 그 경계를 충분히 검증·설명하지 못한 데 있다. 조사한 문서·세션에서 “새 C++가 전혀 없다”는 직접 보고는 찾지 못했다. 확인된 증거만으로 의도적인 기만 여부를 판단할 수 없다.

## 5. 원인과 빠진 통제

직접 원인은 구현자가 기존 데이터 제작 경로를 먼저 완성하는 대신, 기능을 동작시키는 C++ 등록·이미지 처리·표시 분기를 추가한 것이다. 그 뒤 검사와 보고가 이 별도 구현의 작동 여부를 중심으로 이어졌다.

초기 구현·최초 보고에서 다음 구조 검증이 부족했다. 해리어 오류 정정 이후 보고 그림과 런타임 해시 검사, 입력·출력 manifest가 추가됐다. 그 보완을 포함하더라도 원작 제작 규칙과 전 플랫폼 최종 표시까지 연결한 검증은 완성되지 않았다.

- 원작 MCH/MAP writer→기존 parser 왕복과 실제 런타임 소비 경로 비교.
- 채택 원본→생성 입력→게임용 파일→배포 패키지→화면까지 동일 파일과 처리 조건을 연결하는 검사.
- 이름 기반 신규 분기와 원작 공통 경로의 범위 검토.
- 실제 PNG 픽셀 접합·플랫폼별 최종 텍스처·실전 사격 궤적을 포함한 검증.
- 보고의 “재사용”, “같다”, “해결”이라는 문장이 각각 어떤 증거까지 말하는지에 대한 확인.

기존 검사 중 hitbox 내부에서 시작하는 탄, 소켓·사각형의 수학적 겹침, 파일 존재와 draw 명령 검사는 해당 좁은 기능을 확인했다. 이들을 에셋 제작 절차와 원작 구조의 동일성을 확인한 검사로 확대하면 안 됐다. 당시 CI에도 원작/신규 자원 계약의 동등성을 강제하는 검사가 없었다.

브랜치 절차에 관해서는 이번 감사에서 주요 릴리스의 develop→main 기록을 확인했다. 확인되지 않은 브랜치 위반을 이번 원인으로 추가하지 않는다. 사용자는 후속 핫픽스에서도 작업 브랜치→develop→main을 지키라고 다시 명시했다.

## 6. 시정 계획과 현재 상태

[핫픽스 계획](new-unit-hotfix-plan-20261109.md)에 현재 화면 기준 확보, 원작 형식으로 표현 가능한 정의·배치 이전, 공통 파츠 표시, 원작에 없는 동작의 명시적 공통 계약, 전 플랫폼 검증·PR·정식 배포·복귀 절차를 담았다.

현재 채택 그림과 움직임을 유지한다. 과거 시안으로 돌리거나 원작에 없는 동작을 없애 외형을 바꾸는 방식으로 처리하지 않는다. 동시에 현재 코드 구조를 그대로 둔 채 문구만 정정하는 것으로 완료하지 않는다.

원작 저자의 원화 도구·빌드 스크립트 전체는 확보되지 않았다. 대조할 수 있는 근거는 출하 자원 형식·기존 데이터·분석한 동작과 현재 복원 코드다. 이 한계를 밝히고, 확인 가능한 파일 계약과 소비 경로를 실제로 통일한다.

완료한 것은 감사, 소스·자원 기준 보존, 계획·경위 기록이다. 핫픽스 구현·시각 동등성·실기기 검증·main 배포는 남아 있다. 후속 결과는 검사한 커밋·플랫폼·조건과 실패/미검사 항목을 함께 기록한다.
