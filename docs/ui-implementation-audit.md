# 게임 UI 구현 조사 — 2026-11-01

11월 1일 조사 뒤, 11월 2일 추가 게임 버튼 전체를 원작 버튼 절차로 교체하라는 지시를 받았다. `fix/pwa-transfer-fullscreen`에서 구현하고 플랫폼별 검사를 진행한다. 아래 표는 교체 전 조사 기록이다.

## 조사 대상과 구분

| 대상 | 교체 전 경로 | 조사 항목 |
|---|---|---|
| 멈춤 메뉴 SET GAME UI | 원작 GameMenuSub 스프라이트 영역 조합, 게임 렌더러·눌림·터치 판정 | 비교 기준으로 보존 |
| HUD 편집 도구 | Apple editorButton, Android metalButton, 웹 자체 편집 UI | 생성 시점·문구 변경·렌더·입력 경로를 플랫폼별로 대조 |
| 복원 진입 버튼 | Apple은 editorButton, Android는 metalButton 호출; 웹·Tauri는 공통 HTML/CSS | 생성 함수 공유와 화면 배치·노출 조건·이벤트 연결을 각각 기록 |
| 코드 입력·출력 | 플랫폼 입력창·클립보드·파일 선택 연결 | OS 연동이 필요한 부분을 구체적으로 표시 |
| 치트 패널·키 설정·오류 안내·시작 화면 | 별도 네이티브/HTML UI 후보 | 전수 목록을 만든 뒤 기존 게임 UI로 가능한지 판단 |

HUD 편집 도구와 복원 버튼은 생성 함수를 공유하는 부분이 있어도 같은 화면 절차가 아니다. 복원 버튼은 슬롯 화면 조건으로 표시하고 복원 대화상자를 연다. HUD 도구는 편집 상태·레이아웃·도구별 동작을 따른다. 이 차이를 생략해 같은 구현이라고 보고하지 않는다.

교체 전 Android 버튼은 Kotlin에서 프로그램으로 생성한다. XML 레이아웃을 쓴 것으로 단정하지 않는다. 조사에서는 XML·Kotlin UI·UIKit/AppKit·HTML/CSS를 실제 파일과 호출부로 식별한다.

## 조사 방법

1. Sources/iOS, Sources/Web, Android/app/src, Desktop/Tauri/frontend, Distribution/Web, Modules/SaveTransfer에서 표시되는 UI와 생성·입력·표시 호출부를 모두 열거한다.
2. 각 항목에 소비 플랫폼, 진입 화면, 에셋/폰트, 생성·갱신 주기, 눌림 상태, 터치 판정, 키보드 포커스, 저장 호출 여부를 기록한다.
3. 기존 게임 버튼·텍스트·메뉴 구현으로 처리할 수 있는 항목과 클립보드·IME·파일 선택 등 OS 연결이 필요한 기능을 구분한다. 단순 버튼·장식은 별도 네이티브 UI가 필요한 근거로 삼지 않는다.
4. 게임 UI로 옮길 후보마다 제거 가능한 중복 코드, 수정 파일, 입력·좌표·수명주기 위험과 검사를 제시한다. 기여자 커밋은 보존하고 후속 변경은 별도 커밋으로 남긴다.
5. 매 프레임 이미지 생성·디코딩·파일 쓰기, 숨긴 UI의 갱신, 중복 입력 처리도 확인한다. 실제 성능 계측과 코드 검토 결과를 구분한다.
